# Working on Solis

Solis is a 3D game engine. Read DESIGN.md before any change; it is the plan, and its decision log records what's settled.

## Start of every session

1. Read `README.md` (what's built, what's next), `ROADMAP.md`, `ARCHITECTURE.md` and `CONTRIBUTING.md` (the ground rules).
2. Read the README of every crate you will touch.
3. Check `docs/decisions/` before changing anything a decision covers.

## Rules

- **THE SCOPE RESET COMES FIRST** (the project lead, 2026-11-21, decision 0135): read [docs/plans/scope-reset.md](docs/plans/scope-reset.md) before anything else. Solis is a small, simple engine judged by the games it makes well. The done list is written (a farming game like Stardew Valley, a platformer and a 2D combat game), and since 2026-11-26 the order is **tiny first, cheapest game first** (decision 0138; [the target](docs/plans/scope-reset.md#the-target-tiny-versions-cheapest-game-first)): the "Can I make this?" check, the platformer, the action platformer, removing Rust and Lua as game languages, the farming game's small pieces, then dialogue in full. Each feature in its smallest version, grown when a game needs more. New game code is Lust only, most changes take the light path, and the big-engine goals are parked; the dialogue system stays. Where that plan and a rule below disagree, the plan wins.
- **The uniformity pass comes after Fixes 3, before dialogue** (the project lead, 2026-11-23): one look for each kind of element, parts built once and reused, and the engine's calls in Lust rethought without long dotted names. ## Builds (decision 0018)

The repo is public, so GitHub's machines are free (decision 0018, which replaces 0001).

- Checks run on every update to a non-draft pull request and on merges into main, skipping docs-only changes: formatting and licences, then lints, tests and docs on Windows. The Linux build jobs (tests, GPU tests, the window test) are paused until the engine is much further along (decision 0102), so the local run below is the only one they get. A weekly security check and Dependabot keep dependencies safe. The Windows EXE is built when code is merged into main (decision 0010). Solis is made for Windows only (decision 0012); no macOS.
- Keep workflows cheap anyway: cheap checks first, cancel older runs, cache builds, pin actions by commit.
- Run the full checks locally before pushing, and list the results in the pull request: `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, `cargo deny check`, the GPU tests with `REQUIRE_GPU=1`, and `tools/smoke/window-smoke.sh` under `xvfb-run` (see ARCHITECTURE.md, Checks).

## Code

- Follow every ground rule in `CONTRIBUTING.md`; CI enforces many of them, review enforces the rest.
- Tests for every batch (normal, edge, failure, regression, round trip, fuzz, benchmarks as relevant), and the whole suite run before pushing. Anything that reads files or saved settings gets a fuzz test.
- Update documentation in the same pull request: code comments, crate READMEs, `ARCHITECTURE.md`, `CHANGELOG.md` (CI checks it), the **user manual**, and the README progress tracker when a milestone completes. Fill in the pull request template.
- **The user manual is required.** Any change a user would notice updates `docs/manual/` in the same pull request, following `docs/manual/_template.md`. Write for someone new to game engines: explain *why* as well as *how*, and link terms to `docs/manual/concepts.md` (add new terms there). The manual describes only what exists in `main`.
- **The user guide is the manual, built** (decision 0112): every change a user would notice updates the manual in the same pull request, and the guide is generated again (`cargo run -p user-guide`, which writes `docs/user-guide/index.html`); the check fails otherwise. A new manual page goes into `docs/manual/SUMMARY.md`, in its group, and keys are written `` `Ctrl + K` `` (`docs/manual/_template.md`). New game-code examples are in Lust alone (`lust`; decision 0135); those already in Lust, Rust and Lua (three fenced blocks, `lust`, `rust`, `lua`) stay, and the guide's pictures are taken again with `tools/guide-pictures/take-pictures.sh` (after `cargo build -p app`) **once a phase, at its end** (decision 0115, amending 0113): between phases, pictures older than the interface are only a note in the suite; missing, unused, oversized or uncaptioned pictures fail every run.
- **Code review (decision 0027):** at the end of each phase (before its gate) and whenever the project lead asks, run three separate reviewers over the code since the last review: stability, efficiency, and correctness where parts meet. Check each finding, then fix them in pull requests grouped by kind, with the scale check and new scale cases for slow spots found.
- **Scale check:** at the end of each phase, and whenever the project lead asks, run `tools/scale/scale-check.sh` and put its table in the pull request (decision 0011). Not on every pull request. At the end of each phase, also take the guide's pictures again and run `GUIDE_PICTURES_STRICT=1 cargo test -p user-guide`, which fails if they're older than the interface (decision 0115).
- **Every folder has a `README.md`** saying what's in it and how its parts fit (CONTRIBUTING.md, documentation). Read it before working in a folder, and update it in the same pull request when files are added, removed or renamed. Folders read as data (game assets, fuzz seeds, test data, the manual, fonts) are described in their parent's README instead. These READMEs and this file are updated with every change and are always current (decision 0095).
- Any new place the program's name must appear gets added to `RENAMING.md` in the same pull request.
- The pull request's "How to test" list covers what automated tests can't (feel, looks), written for a non-programmer.
- Never hard-code the program's name: use `crates/app/src/branding.rs`.
- **Game code's calls follow [docs/game-api-guidelines.md](docs/game-api-guidelines.md)** (the project lead, 2026-10-28; decision 0065), the source of truth for every engine call: methods on things, the project's names as states, anything made in an editor reached through a Lust file the editor writes, never a string name. Check every new call against its checklist (CONTRIBUTING.md, rule 25).
- Ask the project lead before building a feature that adds keys or mouse actions: offer a recommended choice and alternatives (CONTRIBUTING.md, rule 17).
- **Choices come as questions** (the project lead, 2026-11-11): every choice goes to the project lead as a question to click, one per choice, with the pictures named in it, never as a list in a message.
- **Merge every feature yourself** (the project lead, 2026-10-28). Once a pull request's CI checks are green, merge it without waiting, and tell the project lead in exactly these words: "Pull request N is merged and checks passed. Next up: X". Its "How to test" steps go into the project lead's testing document, [Solis: things to try by hand](https://claude.ai/artifact/USEHoEYDqbVrNXJUBZ8T8g) (a Claude Doc, edited with the docs tools), as a new section at the top, newest first: a tick box per step, naming the pull request. Read its comments at the start of a session: they are the project lead's findings to fix. The project lead tries everything in one big testing pass once 2D and the effects suite are complete (2026-10-28); until then their only input is answering questions about architecture and signing off UI mock-ups, so don't wait on them for anything else.
- **UI is mocked up first** (the project lead, 2026-10-27). Before building any UI (game UI's canvas and screens, a new editor panel, tool or window), make a mock-up for the project lead to see and approve. The source of truth for the editor's look is the project lead's own design in `docs/design/g-layout/` (the specification and its thirteen screens; decision 0099). Parts it lacks are drawn in its language on its screens and approved before building. Mock-ups are in-chat pictures or a Design artifact, never built code.
- **Rules from the project lead's video editor project** (2026-11-10, decision 0095), in CONTRIBUTING.md: no name-dropping (rule 20), readable code without heavy commenting (rule 3), and competing approaches compared for big systems, where fast, smooth and robust is the bar (rule 22).
- Aventail's code may be copied in and adapted (decision 0007).
- **One line of work** (the project lead, 2026-10-25): Solis is built one milestone at a time on one main thread, never by several agents building parts in parallel. A helper agent may take one specific, bounded job alongside it (the three end-of-phase reviewers, a search, a check) and hands its result back. The next milestone's builder may start reading and writing in its own worktree while the last pull request's full checks and CI run, but builds only once those checks are finished (the project lead, 2026-11-14); still only one builder at a time.

## Local environment notes

- If rustup cannot download the pinned toolchain, run commands with `RUSTUP_TOOLCHAIN=stable` when the installed stable version matches `rust-toolchain.toml`.
- With no GPU, run the editor and GPU tests on Mesa's software driver: `WGPU_BACKEND=gl` under `xvfb-run`.
- Copies of the code (git worktrees) share one build folder. Before building or checking in a copy, run `git ls-files -z | xargs -0 touch` in it: cargo otherwise reuses what another copy built and tests old code (found 2026-11-14).
