# Architecture

Solis is a Rust program split into small, single-purpose crates. **Lower layers never depend on higher ones**, so each piece can be built, tested and replaced on its own, and games can ship without the editor. The `layer-check` tool enforces this on every change.

## Layers

| Layer | Name | Crates | Rule |
| --- | --- | --- | --- |
| 3 | App | `app`, `updater` | Opens the window, owns the frame loop, wires the rest together. No feature logic. `updater` finds, downloads and checks new builds on GitHub (decision 0043). |
| 2 | Editor | `editor` | The editor's interface: top bar, dockable panels, status bar, theme. Never needed by a game. |
| 1 | Engine | `render`, `assets`, `asset_db`, `world`, `script`, `physics`, `input`, `sound`, `animation`, `tiles`, `ui` | What games run on. Knows nothing about the editor. `assets` reads model files; `render` draws; `asset_db` keeps the project's assets by stable ID; `world` holds the running game's entities; `script` runs game code; `physics` wraps Rapier (3D, and Rapier2D for 2D in `physics::flat`); `input` turns keys and buttons into named actions; `sound` wraps Kira and reads sound files; `animation` plays clips of frames by time and reads sprites' clips files; `tiles` holds tilesets and tile maps, reads their files and autotiles; `ui` lays game UI's screens out on any screen. |
| 0 | Core | `reflect`, `area` | Shared building blocks with no GPU, window or interface. `reflect` holds IDs, values and component schemas; `area` holds the area document and the built-in components. |

Each crate's `README.md` states its purpose and what it **must never** do. Read it before changing the crate.

Planned: a networking crate in a later phase. See ROADMAP.md.

## The area

The editor edits a **area document** (`area::Area`): entities by stable random ID, each with a name, a parent, an order among its siblings, and components stored as plain values (`reflect::ComponentData`). A component's fields are described by a **schema** looked up by name in a `reflect::Registry`, so Properties draws any component (built-in now, Lust and Lua later, registered through `Workbench::register_component`) without knowing it, and a component nobody registered is kept untouched and shown as missing ([decision 0019](docs/decisions/0019-scene-document-now-game-storage-later.md)). Built-in components (`Transform`, `Light`, `Model`, `Environment`) are Rust structs that convert to and from their values.

Panels never change the document: Properties returns `PropertyRequest`s and the Area panel `AreaRequest`s, and the workbench turns them into commands. Properties shows values, not buttons ([decision 0085](docs/decisions/0085-the-editor-overhaul.md)): each component in a card whose **?** opens its manual page (`properties::manual_page`) or, for game code, whose **Open in Ledger** asks the app to open the file it's written in (`Compiled::places`, `PropertyRequest::OpenCode`); a field off its schema's default gets a dot and a reset (`inspector::moved_from_default`), and a file several entities use says so (`inspector::users_of`). What only changes how the editor shows the area (the Area panel's search, folded, hidden and locked entities, like the selection) lives in the editor and is never saved or undone; hidden entities are left out of the viewport's `AreaView` and locked ones get no pick number. A command is a list of reversible `area::Edit`s applied through `Document::edit`, the only way the area changes, which records it as one undo step in `area::History` ([decision 0022](docs/decisions/0022-undo-as-reversible-edits.md)). A drag is one step: changes carry a merge key of (what's changed, which mouse press), and steps with the same key in a row merge. The app draws frames back to back only while `Workbench::wants_frames` says something moves (the game running, flying, a held key or button, a drag, a pick on its way); ten a second while background work waits; otherwise one a second ([decision 0026](docs/decisions/0026-draw-only-when-something-changes.md)). The document keeps what's worked out from the area until it changes: its `area::Tree` (children in order, tree order, the first of some entities; again only after entities are added, deleted or moved to another parent), every entity's world matrix (once per revision), and a `shape` revision that ignores value changes other than which model a Model shows, which is what Problems follows. Undo steps are shared (`Arc`), so copying the history (Play) is cheap, and a step's selections count toward its limit (`area::Weigh`). Each frame the workbench turns the document into an `AreaView` (models to draw, the sun, lamps placed in the world, the environment), which the app maps to the renderer's types: each model becomes a `render::Placement` (the uploaded model and its entity's world matrix). The renderer gathers every mesh copy of every placement into one instance buffer per frame, grouped so each mesh is drawn once for all its copies, mirrored copies with front-face-flipped pipelines ([decision 0021](docs/decisions/0021-asset-database-and-models.md)). Only what's seen is drawn: each copy's ball is checked against the view, and against the part of the world in view where shadows fall (up to 200 m away) swept along the sun's light, so copies out of view aren't drawn and only those that can cast into it go into the shadow map, which is fitted to that part (`render::instances::Cull`, `render::sun_view_fitted`). A copy is three rows of its placement (52 bytes), and a frame sends the GPU only the runs of copies that changed. Entities game code makes (`spawn`) and removes (`despawn`) land at the end of the tick that asked, in order, as changes to the area that aren't undo steps (`Document::edit_by_game`) and straight into the world (`World::add_subtree`, `World::remove_subtrees`), so their components run from the next tick and Stop takes them away with everything else ([decision 0035](docs/decisions/0035-game-code-spawns-into-the-area-while-playing.md)); the app reads every assembly in the project when it opens, so any can be spawned. Projectiles game code fires (`fire`) live in the world (`world::Projectiles`), are moved in jobs once per tick, and are drawn in the Game panel in one instanced draw (`render::Bolt`, made from them in `GameScene`). Far copies draw simpler levels of detail, made on import with meshoptimizer and kept in the import cache, or the model's own `_LOD1` meshes ([decision 0032](docs/decisions/0032-lods-made-on-import-or-the-model-s-own.md)): each copy gets the simplest level that strays less than a pixel on screen. A model's own node tree places its meshes inside it; one imported model is one entity until it's unpacked (with assemblies).

## How a frame runs

1. **Input:** winit delivers mouse and keyboard events to egui (through eframe).
2. **Editor:** the workbench draws the top bar, the status bar (`status_bar.rs`: `Workbench::status` works out what it says, apart from drawing) and the docked panels, in the standard arrangement of the editor overhaul ([decision 0085](docs/decisions/0085-the-editor-overhaul.md); `layout::standard`), one layout per workspace (`workspace::Workspace`: Level, Animate, Code; the others' layouts kept in `Workbench::other_layouts`, all saved together as `Workspaces`), and returns any actions (such as Quit) for the app to carry out.
3. **Camera:** the viewport turns the mouse and keys into a `FlyInput`, and `Camera::fly` (in `editor/src/camera.rs`) moves the camera.
4. **Imports:** File > Import model (or a file dropped on the window) asks the app to import; the app reads the file with `assets` on a thread of its own, then uploads it with `render` and tells the workbench, which lists it (with any lamps the file carries) and frames the camera on it.
5. **Viewport:** the viewport panel asks a `ViewportRenderer` for an image of its size, with the sun's settings and the lamps. The app's implementation renders it with `render` on the window's own GPU device (first the sun's shadow map, then the view) and hands it to egui as a texture.
6. **Closing:** eframe saves the window size, the panel layout, the camera, the look and the sun's settings in a per-user folder named after `APP_ID`.

## The Profiler and the scale levels

The Profiler panel (`editor::profiler`) times each frame the editor draws: `Workbench::show` starts and ends the frame, `run_game` times game code (syncs and ticks) apart from the world, the views' preparation is timed where `AreaView`s are built, and a wrapper around the `ViewportRenderer` times handing frames to the GPU; the rest is the editor's. The renderer reports what it drew (`render::FrameStats`) and, on cards with `TIMESTAMP_QUERY` (asked for by the app when the card has it), each pass's GPU time (`render::GpuTimes`), read back a frame or two later without waiting. The scale levels (decision 0030) are timed headless from the same Profiler (`editor`'s `scale_levels_tests`): whole editor frames of 1/60 s while a fleet of Lust-driven units plays.

## The job system

Work that can be split runs in jobs on every core (`rayon`, decision 0031), in one pool the app starts with the window (`app::window::start_jobs`: one worker per core, leaving one for the window). Jobs only ever write their own part of the result, and anything put together keeps a fixed order, so a frame is the same on one core or sixteen (tests compare both). Today: the game's view (`AreaView::of_world`) and gathering the GPU's copies (`render::instances::gather`).

## Colour in the viewport

The world is drawn in linear HDR colour (brighter than white allowed) into a 16-bit floating-point image, with multisampling. A last pass (`post_fs` in `crates/render/src/viewport.wgsl`) applies exposure and tone mapping (AgX, ACES or none) and converts to sRGB into a plain 8-bit RGBA image, which egui shows as it is ([decision 0017](docs/decisions/0017-hdr-tone-mapping-sky-and-fog.md)). The shader converts to sRGB itself, because letting the GPU do it would need a second "view" of the image in another format, which older and software GPUs (OpenGL) can't make, and the editor has to open on those too.

The HDR image's alpha channel is a mask, not opacity: 1 where the lit world is (tone mapped), 0 for the editor's backdrop and the lines over it (shown exactly as the theme has them). Lines and the grid therefore blend their colour only and leave alpha alone, and they pick an opacity that looks the same as blending in sRGB (`overlay_alpha`), as the mockup was drawn.

## Updates

The Windows EXE workflow (`.github/workflows/windows-exe.yml`) builds the program on every merge into main with `BUILD_NUMBER` set to its run number, makes an installer with Inno Setup (`installer/setup.iss`, per user into `%LOCALAPPDATA%\Programs` or a folder the user picks, leaving `installed.txt` beside the program), writes its SHA-256 beside it, and publishes both as GitHub release `build-<number>`, keeping the newest ten ([decision 0043](docs/decisions/0043-installed-and-updated-from-github.md)). The name, ID, repository and installer's name are read from `branding.rs`.

In the program, `updater::this_build` is the stamped number (none when built any other way). While the splash screen shows (at least 0.6 s, [decision 0045](docs/decisions/0045-a-splash-screen-that-asks-before-updating.md); `app::startup` is its logic, `editor::splash` draws it and the update question), `updater::start` asks `api.github.com` for the latest release on a thread (unless the person turned Help > Check for updates when starting off), reads it with limits and only trusts download addresses on the repository's own releases (`updater::release`). A newer build that isn't the one skipped brings up the question; Update now runs `updater::start_download`, which downloads the installer over HTTPS (ureq with rustls, checked by the system's certificates), checks its SHA-256 and keeps it in `%LOCALAPPDATA%\<id>\updates`; the window then closes and `window::run` starts the installer quietly with `/RELAUNCH=1`, which opens the new build. Each step comes back on a channel and wakes the window. Once the editor is open, `app::updates` takes over: Help > Check for updates asks the same question, Update now downloads while the person works, and Restart to update (`editor::updates`) or closing installs it.

## Checks

- `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` and `cargo deny check` run locally before every push.
- `crates/render/tests/gpu.rs` renders real frames. Without a GPU it skips; with `REQUIRE_GPU=1` a missing GPU is a failure.
- Fuzz tests feed thousands of randomly damaged inputs (saved layouts, saved cameras, command lines) to everything that reads them; none may crash.
- **Whole-game invariant tests** (`crates/editor/src/invariant_tests.rs`, [decision 0042](docs/decisions/0042-a-hardening-milestone-before-phase-7.md)) play random games (walking, jumping, spawning, saving and loading, edits while playing, pausing and stepping, code swaps) on a small level and check rules that must always hold: a loaded game carries on exactly as the saved one did, tick by tick; a recording replays exactly; Stop puts the area, undo history and selection back; nothing is left broken. `physics` checks the same way that characters moved together end where one-by-one moves put them. A failure is shrunk to the shortest game that shows it and kept in `proptest-regressions/`, tried first ever after. `PROPTEST_CASES` sets how many games (12 by default; more in the weekly run).
- **Fuzzing** (`fuzz/`, see its README) feeds every reader of a file a project can ship millions of changed copies of real files (`fuzz/seeds/`, most made by `fuzz/make-seeds.sh`): saves, recordings, input actions, areas, models, the import cache, sidecars, the project file, game code, sounds and buses, sprites, tilesets and tile maps, text files and screens (the README lists every target). It needs `cargo-fuzz`; `fuzz/run-all.sh` runs every target, and so does the weekly run (`.github/workflows/deep-checks.yml`), which reads its targets from `fuzz/Cargo.toml`. The fuzzers are their own workspace, but keep no lock file of their own: `tools/ci/fuzz-lock.sh` writes it from the main `Cargo.lock` before they are built, so they build the library versions the program ships.
- **The updater against the real GitHub**: `updater` has two tests that need the internet (asking for the newest build, and downloading its installer and checking it against its published SHA-256, without starting it). `cargo test` and pull requests leave them out, so the network can't fail a pull request; the weekly run (`.github/workflows/deep-checks.yml`) runs them on Windows.
- `tools/scale/scale-check.sh` times the editor and the viewport against their targets, at every phase gate and on request ([decision 0011](docs/decisions/0011-scale-check-at-phase-gates.md)).
- `tools/smoke/window-smoke.sh` opens the real editor on a virtual screen, flies the camera, drags a panel, quits and reopens, and checks the layout and camera came back.
- CI (`.github/workflows/ci.yml`) runs all of these on every update to a pull request and on merges into main, on Linux and on Windows (Direct3D 12 through WARP for the GPU tests) ([decision 0018](docs/decisions/0018-checks-for-a-public-repo.md)). `.github/workflows/security.yml` checks for security advisories weekly, and Dependabot opens grouped update pull requests weekly.
- `.github/workflows/changelog.yml` fails a ready pull request that changes code without a `CHANGELOG.md` entry, unless it is labelled `internal`. It also runs `tools/ci/breaking-check.sh` (Phase 8, C5): a new version of a file format (the newest `tests/fixtures/<format>/v<N>/` goes up) or anything taken away from `docs/game-code-interface.txt` needs a new line under `### Breaking` in the Unreleased part, labelled internal or not.
- `.github/workflows/windows-exe.yml` builds a downloadable `solis.exe` when code is merged into main, and by hand ([decision 0010](docs/decisions/0010-windows-exe-on-merge.md)).
- `.github/workflows/sources.yml` saves the source of every library whenever `Cargo.lock` changes on main, as a pre-release `sources-<hash>`, keeping five ([decision 0052](docs/decisions/0052-dependency-safeguards.md)).
- `tools/layer-check` also checks the dependency register (`docs/dependencies.md`): every outside library listed, and used only in the crates its row allows.

## Conventions

- **Z is up.** X is red, Y green and Z blue wherever axes are shown.
- **Units are metres.**
- **The engine never waits on the GPU or on files in the frame loop;** slow work runs on other threads and reports back with messages.

## Picking and gizmos

Each model the viewport draws carries a pick number (`editor::ViewModel::pick`). A click or a box in the viewport asks the renderer about a rectangle of the image (`ViewportView::pick`); `render` draws the placements once more into a small ID image (each pixel: the placement's number and its depth), inside that rectangle only, and copies it back without waiting (`ViewportRenderer::request_pick`, `ViewportTarget::poll_pick`). The answer reaches the editor a frame or so later (`ViewportRenderer::picked`), which turns numbers back into entities with the list it kept when the question was sent (not when it was asked: the area may change in between), and applies the selection rules in `editor::picking`. Each answer carries the rectangle it was asked about, and one for an older question is ignored; a question the renderer refuses (a resized view) is answered empty, so nothing waits forever. Lamps are picked by their markers on screen instead.

The gizmo's maths (`editor::gizmo`, from Aventail) turns mouse movement into a change; `editor::transforming` works out each moved entity's new Transform from where it was when the drag began, and the workbench writes it as `SetField` edits merged by the drag's gesture, so a drag is one undo step and a cancelled drag leaves none ([decision 0025](docs/decisions/0025-picking-and-gizmos.md)). The viewport only reports what the mouse did (`ViewportEvent`s); the workbench changes the area.

## Projects and assets

A project is a folder: `project.solis`, `assets/` and the `.solis/` cache. `asset_db::AssetDb` is worked out from `assets/` (the folder is the truth); each asset's `AssetId` lives in a `.solmeta` sidecar beside it, so renaming, moving or switching Git branches breaks nothing. The app (`crates/app/src/project.rs`) holds the database and a watcher; when the watcher reports something, the database rescans and the app reloads changed models in use on worker threads, through the import cache, and swaps them in by ID. A model imported while a project is open (the sample area too) is copied into `assets/` first, and given its sidecar at once (`AssetDb::adopt`). A new file found without a sidecar waits until it has been still for `asset_db::SETTLE` (two seconds; `AssetDb::look_again_at` says when to look), because Git writes a file and its sidecar one after the other and a look in between would give it a new ID. Files sharing one ID (copied with their sidecar) leave it with the one the database knew, or else the one whose sidecar is oldest. The import cache keeps within `asset_db::cache::MAX_BYTES`, trimmed on a worker when a project opens (least recently used first). The editor only sees `ProjectInfo` and the Library's list ([decision 0021](docs/decisions/0021-asset-database-and-models.md)). The Library lists every file (`AssetDb::listing`), and asks the app to rename, move, delete (to the Recycle Bin) or open them through `WorkbenchAction`s; `asset_db` moves a file's sidecar with it. Thumbnails (`crates/app/src/thumbnails.rs`) are made a few at a time: pictures shrunk on a worker, models read on a worker and drawn once on the GPU into a small texture egui shows. A model dropped from the Library is placed where the viewport's picking finds the surface under the mouse (`ViewportEvent::Drop`); the editor remembers the spot until the app has loaded the model.

Text files (`asset_db::TEXT_EXTENSIONS`, `FileKind::Text`) are shown in Properties: the app reads the one picked (`app::text_files`, again when its size or time changes, at most 512 KB) and hands it over (`Workbench::set_text_file`); `editor::text_view` draws Markdown from its own small reader and the rest as plain text, and the Library opens them in the computer's program for them, since they only ever show text.

The Library makes new files itself (E1, [decision 0070](docs/decisions/0070-usable-first.md)): **New** (right-click anywhere in it, or **+ New**) asks the app to write a Lust code file or an empty area (`WorkbenchAction::NewTextFile`, `Projects::save_new_text`, which never replaces a file and only writes `.lst` and `.solarea` inside the assets), then opens it: a code file in the computer's program for `.lst` files (Ledger), an area in the editor. Tile maps, tilesets, animators and sound events are made as before. The launcher (`editor::launcher`, [decisions 0086](docs/decisions/0086-the-launcher.md) and [0090](docs/decisions/0090-always-through-the-launcher.md)) shows every time Solis starts, when the editor's window is closed (the app turns the close into `Workbench::back_to_launcher` unless it's quitting: the launcher's own close, File > Quit, Restart to update), and from File > Projects…; the app sizes the one window for it (`App::fit_window`: the launcher's 1100 × 700, or the editor's size as last left, saved per computer, centred on the monitor). Updates are checked as Solis starts without a question (`Updates::adopt`), and a newer build is a bar over the projects. The app keeps every project it knows (`app::known_projects`: folder, pin, when last opened, up to 200, read once from the old recent list) and reads each one's project file for the launcher (`asset_db::Project::summary`): its name and `saved_by`, the build that last opened it, which `Projects::open` writes (`Project::record_build`, keeping the file's other keys). Renaming, copying and scanning are `asset_db::tidy`: a rename changes only the project file's name, a copy leaves out the import cache and links and never goes into a folder that isn't empty, and a scan stops at a depth and a number of folders; copies and scans run on a worker (`known_projects::Tidying`) and report through `Workbench::launcher_notice`. The Updates page draws the editor's `UpdateNotice` and the newer build's `ReleaseNotes` (its release's text and day, read by `updater::read_release`); its buttons are the Help menu's actions. Each build's release text names the pull request merged (`.github/workflows/windows-exe.yml`).

## Sound

The `sound` crate wraps Kira ([decision 0056](docs/decisions/0056-sound-with-kira.md)), as `physics` wraps Rapier: nothing else sees Kira's types. Kira's own file reader (symphonia, MPL) is off; `sound::read` reads WAV with `hound` and Ogg Vorbis with `lewton` within limits (256 MB, 8–192 kHz, up to 8 channels, more than two mixed to mono, every sample clamped and NaN made silent), and makes an `Overview` (each stretch's lowest and highest sample, at most 2,048 of them) in the same pass for drawing the waveform. A sound longer than ten minutes, or 16 million frames (128 MB), isn't kept in memory: it's streamed from its file as it plays. A file holding more than one Ogg stream (a chained Ogg) is refused, since `lewton` would read the later streams' headers unchecked; a streamed Ogg is opened afresh to start again, as `lewton`'s own seek to 0 lands on the headers; and a streamed file shorter than measured is padded with silence to its measured length (Kira asks until then), while one whose rate or channels changed is refused. `SoundDevice` holds Kira's audio manager (the sound card, a mock device in tests, or none) and previews on an Editor track of its own. The app opens the card on a worker (`crates/app/src/sound.rs`), uses a silent device until then or when there's none, and tries again every 30 seconds. `crates/app/src/sounds.rs` measures each sound file in the project on a worker (`sound::measure_file`: its details and overview, never its samples) and hands the editor `SoundState`s; listening plays the file streamed from disk (`Clip::streamed`), so it starts at once whatever its length, and the app tells the editor each frame how far it has got (`Workbench::set_preview`). The editor (`sound_view.rs`) draws the waveform on Library tiles and in Properties, which shows a sound picked in the Library until the area's selection changes. Sound events (`sound::event`, S2) are `.solsound` files read and written with `area::settings` (the Lust style of areas, as `key = value;` lines): takes by asset ID, volume and pitch with ranges, bus, placement (in the world or everywhere), distances, fade, how many at once, priority and looping. `sound::event::pick` chooses a play from sound's own random stream (SplitMix64 over the seed, the tick and the request's order), never the game's, and never the same take twice in a row; the app reads events on the same worker as sound files and plays a pick with `SoundDevice::preview_varied`. Properties edits an event (`editor::sound_event_view`) and asks the app to save it (`WorkbenchAction::SaveSoundEvent`) once the mouse is let go. Game code's sounds (S3): `playSound…` and `stopSoundsOn` add `Change::Sound` and `Change::StopSounds` to the tick's changes in its fixed order (at most `script::game::MAX_SOUNDS` a shard a tick); the editor's host gathers them (`PlayWorld::sounds`) and `editor::game_sound` numbers them with the tick and seed for the app (`Workbench::take_game_sounds`), with the listener (the first camera, drawn between ticks) and entities' places between ticks. `app::game_audio` picks each play with `sound::event::pick` (seed, tick, order), skips those past their far distance and, after a stall, all but the last few ticks', and plays them with `sound::game` on Kira spatial tracks under a game track that pauses with the game (a Step's sounds go on a second track). Places and the camera's turn go to Kira unconverted: a Camera looks along its -Z with +Y up, as Kira's listener does. Short sound files are decoded into memory on the measuring worker (up to 512 MB in all); longer ones stream. Nothing flows back into the game or its checksum. Ogg files' headers are checked before `lewton` reads them (`sound::vorbis_check`), because `lewton` sets aside memory for whatever counts a header claims. Kira needs `triple_buffer`, which is MPL-2.0, so Solis stands in for it with its own MIT crate in `patches/triple_buffer` (`[patch.crates-io]`; docs/dependencies.md, Patches). On Linux the sound card is reached through ALSA, so the checks install `libasound2-dev`.

## The console and Problems

The Console's command line (`editor::console`) hands each line to `editor::console_commands`, which splits it into words (quotes keep a name with spaces together) and runs it with the editor's own commands, so `set` and `delete` are undo steps like the menus'. Its history is a setting the app saves. Libraries write through the `log` facade; the app's logger (`crates/app/src/logger.rs`) queues every warning and error, and information from Solis's own crates, and the window moves them into the Console each frame. `editor::problems` checks the area against the registry, the loaded models, the project's assets and the assemblies; it runs again only when one of those changes (a fingerprint of the history's state, counts and the area's file), so it costs nothing on a frame where nothing changed.

## Game code

A game's Lust lives anywhere in the project's `assets`, starting from `main.lst`, and its Lua components in any `.lua` file there ([decision 0028](docs/decisions/0028-lust-runs-as-luau-while-editing.md)). The `script` crate (layer 1) knows the native methods Solis gives game code (`script::describe::NATIVES`) and writes them as Lust files into `assets/solis/` (the folder name is `branding::CODE_FOLDER`) when a project opens. Natives follow the game API guidelines (decision 0073): an entity's abilities are `entity` methods (`Native::owner`), the rest sit on engine objects (`World`, `Saves`), and their bodies are lent by `Native::key` (`entity_moveTo`, `World_say`). Beside them the app writes `solis/project.lst`, the project's assemblies as `state Assembly` (`script::project_names`), again whenever the assets change (`GameCode::describe_again`, only when the text differs), so `World:spawn(Assembly.Ships.Fighter, p)` is checked before the game runs; the native turns the option back into the file's path. The sprites' clips and cues, read on a worker, join it when the sheets change (`SpriteSheets::clip_names`, `GameCode::set_animation`), and each animator gets its own file in `solis/animators/` (`script::animator_code`), whose class a component holds as a field Solis fills in when the component is made (`syncing::make_lust`); its setters land at the end of the tick as `Change::AnimatorSet`, and `current()` reads `WorldView::animator_states`. It also reads a project's code within limits (`script::gather`) and checks it with the Lust compiler used as a library (`script::check`), telling Lust which folder is the engine's (its host folder, so only those files give `entity` methods) by the first line of the files Solis wrote there (`describe::engine_folders`, decision 0072). The compiler's notes (older ways of writing that still work, such as `me` for `this`) go to the Console as warnings, once each time they change (`Workbench::set_program`). The app (`crates/app/src/game_code.rs`) does both on a worker when a project opens and whenever the watcher reports a change, and hands the editor the mistakes only when the code differs from the last check (`Workbench::set_code_problems`). The Problems panel lists them before the area's problems, and clicking one opens its file. The worker also turns sound code into Lua and starts it on its own to read its components (`script::compile`, on a thread with a large stack; Lust keeps its own nesting limit), and the editor takes it as the program (`Workbench::set_program`): its components join the registry, so Properties, Add component and area files treat them like built-in ones. Pressing Play loads the program afresh in a `script::Game` beside the `world::World`: one `Runtime` per core, each running its share of the entities ([decision 0033](docs/decisions/0033-game-code-sees-the-start-of-the-tick.md)). During a tick, game code reads the world as it was when each phase started (`script::WorldView`, made by `editor::game_code::PlayWorld`) plus its own changes, and what it writes is kept and landed in a fixed order at the phase's end, so the result doesn't depend on the number of cores. It makes each entity's game components from the area, and each frame passes editor changes on (`sync`: only fields that changed) and runs the frame's ticks. After each tick's updates the events sent are delivered in rounds, in order, to each component on the entity in name order (`script::events`). An event no component took whose entity was spawned that tick (its components are made as the tick's spawns land) is held by `script::Game` and delivered first in the next tick's first round (`Phase::unclaimed`). Components written in Rust (`script::RustComponent`, added with `Workbench::add_rust_component`) run in the same ticks and take part in the same events. New code arriving while playing is swapped into the running game first (`script::Runtime::swap`, from `Workbench::set_program`): components keep their values, new ones start, and if the new code fails to start against the game's world the last working program stays, registry and all; only a swap that worked changes the registry. Stop keeps the registry as it is now. A component of the code's whose name is taken (one of the engine's own, or a Rust one's) is a problem and is left out of the runtime (`Runtime::leave_out`). Rebuilding the game's world (an entity added, an undo) keeps where game code moved things unless the area moved them too. Saving to running takes about 0.33 s, most of it the watcher's quiet time (`app` scale check). Lua components (`.lua` files anywhere in `assets`) are syntax-checked on the worker and run in the same Luau, ticks and events as the Lust (`script::lua_components`). The worker also compiles the Lust and Lua to Luau bytecode, so loading at Play and swapping new code in skip compiling on the frame, and it skips compiling altogether when a change in the assets didn't change the code. The editor syncs changed entities in one batch (`Runtime::sync_many`). While playing, Properties shows the selected entity's game code values as they are now (`Game::values` for each of its components, asked on frames Properties is in front, `PanelViewer::running`); an edit there goes through the area as usual and reaches the game by sync. That Luau is sandboxed (`script::luau`): libraries read-only, globals of their own for the Lust and each Lua file, a deadline on every call and on each whole tick and load, watched by an interrupt set on Luau directly (`script::interrupt`, the one `unsafe` module, [decision 0034](docs/decisions/0034-a-raw-interrupt-for-the-time-limits.md)); no `package`/`require`; game text always loaded as text, never bytecode (`luau::as_text`); and the prelude wraps the library loops the interrupt can't reach (`table.move` capped at a million items) and `collectgarbage` (only `"count"`). A problem's file is taken from a Lua error's text only when it's a plain path in the project, and the Library opens only plain paths inside `assets` (`plain_relative`).

**Files from a project are hostile until checked.** A project can be downloaded, so its files are read and written defensively: every write is a new uniquely named file renamed into place (`asset_db::write_atomically`), into folders Solis makes and refuses if they're links (`asset_db::own_folder`: `saves`, `recordings`, `.solis`, the cache, `assets/solis`, `assets/assemblies`); every read is of an ordinary file, never more than its limit even if it grows (`asset_db::read_limited`, `assets` `open_file`); names Solis makes or accepts work on every system (`asset_db::valid_file_name`, `file_name_from`, `assets::reserved_on_windows`); a model's addresses are checked after decoding; the import cache refuses what the importer never makes (`Model::is_finite`); and expansions are counted before they're made (`Expander::size_of`, `MAX_HELD` across nested assemblies, glTF children before listing). A tick past its deadline is cut short and the editor pauses the game rather than catching up. Built games will run the same Lust as Rust. The turret sample (`samples/turret`, made by `crates/app/src/sample_game.rs` from **Help > Make the sample game…**) is the first game: its Lust, Lua and Rust components talk through events. Its Rust component is compiled into Solis from the sample's own `armour.rs` and offered only in that project, until Phase 10 builds a game's Rust ([decision 0029](docs/decisions/0029-the-sample-s-rust-component-is-built-in.md)).

## Several views

The viewport shows one, two or four views (`ViewLayout`), each drawn into its own image (`ViewportView::image`, 0 to 3) by the same renderer. A view's camera may be flat: `editor::Camera` has a `ViewKind` (Perspective, Top, Front, Right) and a zoom height, and its projection, rays and sizes follow it, so picking and the gizmos work unchanged; `render::FrameParams::grid_plane` stands the grid in a flat view's plane. Only one view is in use at a time: its camera, look and tools sit in `Viewport`'s usual fields, and the others are swapped in while they're drawn (`Viewport::show`), so the workbench reads one camera as before. Each view keeps its own picking and dragging state; their events are gathered for the workbench. The layout and every view's camera and look are saved (`Views`).

2D (Phase 9, D1; [decision 0062](docs/decisions/0062-2d-on-the-ground-drawn-small-scaled-whole.md)) lies on the ground, seen from above. A project's 2D settings (`area::pixels::PixelSettings`: base resolution, pixels per unit, tile size, scaling) are read from `pixels.solpix` by the app (`play_files::load_pixels`) and handed to the workbench (`Workbench::set_pixels`), which gives them to the viewport and the Game panel; the Settings window's 2D page changes them and asks the app to save them (`WorkbenchAction::SavePixels`). When the game's camera is a 2D one (`area::builtin::CameraView::TwoD`), the Game panel works out a flat view of the base resolution plus a pixel each side, with the camera on whole pixels (`game_panel::pixel_camera`), and sets `ViewportView::pixel`: the app draws the world into a small target of that size, then `render::ViewportRenderer::draw_pixels` scales it up into a screen-sized `render::PixelImage` as `render::pixel_layout` says (whole steps or fill, slid by the camera's bit of a pixel), which egui shows. The editor's 2D view (`ViewKind::TwoD`) is a flat view whose height comes from its zoom (`Camera::seen`, which also puts its edges on whole screen pixels); its grid is the tile size (`FrameParams::grid_step`) and its moves snap with `transforming::snapped_in_2d`.

Sprites (Phase 9, D2) come from Aseprite files, read as they are. The app reads each `.aseprite` file in the project on a worker (`app::sprites`, with `assets::aseprite` and `assets::sprite_sheet`): frames flattened, trimmed, identical ones kept once, and packed into one atlas with padded edges; again whenever it's saved, a failed read keeping the last good sheet. It uploads each atlas (`render::GpuSheet`) and hands the sheets to the workbench (`Workbench::set_sprite_sheets`), which shows them in the Library and Properties and offers them to a Sprite's fields through the schema's hints (`reflect::Offer`). Each frame, the area view's sprites (`AreaSprite`: an entity's `area::builtin::Sprite` and world matrix; from the running world while playing) become `ViewSprite`s, laid out exactly as `render::SpriteInstance` so they reach the renderer with no copy, in a run per sheet (`editor::sprite_sheets::batches`); in a 2D view or through a 2D camera, where each stands is put on a whole pixel. The renderer draws each run in one instanced call, after the models (`render_scene`). Pixel art is cut out, so sprites write depth and need no sorting: the shader draws one standing lower on screen a hair nearer, so front and behind come free, and see-through ones blend last, back to front. Sprites write alpha 0, which the last pass shows as drawn, so their colours are never tone mapped. Picking draws them by their own pixels (`request_pick_with_sprites`), with the same pick numbers models use. A plain `.png` or `.jpg` is a sheet too (`assets::sprite_sheet::picture_sheet`, one frame), but read only when the editor asks: `SpriteSheets::get` on one not read adds it to `pictures_wanted`, which `app::sprites` drains each frame, so 3D textures are never read as atlases unless a sprite uses them; a picture dropped into the viewport waits in `Workbench::pictures_placing` until it's read. **Parallax layers** ([decision 0094](docs/decisions/0094-parallax-layers.md)): a sprite whose entity has an `area::builtin::Parallax` is left out of `batches` and gathered by `editor::sprite_parallax::parallax_layers` instead: moved to `camera + scroll × (place − camera)` for the game's camera (left where placed in the editor), repeated across the ground in view, flagged `PARALLAX` with `UNDER` or `OVER`, and grouped into layers by speed, slowest first; `in_order` puts layers behind before the tile maps' runs and layers in front after everything, and the renderer's flat pipeline draws them in that order. Picking puts a layer behind at the far end of depth, so it's picked only where nothing else is. Through a 2D camera with at most `game_panel::MAX_SMOOTH_LAYERS` (8) layers, `game_panel::smooth_layers` gives each layer a camera of its own, moved its scroll's share of the way from the camera's start (`GameScene::camera_start`, the first camera in the area as Play was pressed) to where it is, its sprites left where placed; `ViewportView::layers` carries them (`PixelLayer`), and the app draws each into a small picture of its own (the farthest with the sky, the rest and the world's picture `set_layered`, clear where nothing is) and lays them together with `draw_pixel_layers`, each slid by its own bit of a pixel.

Frame animation (Phase 9, D3; [decision 0064](docs/decisions/0064-frame-animation-clips-files-and-tabs.md)) is the `animation` crate: a `Clip` is frames with their milliseconds and events, a direction, repeats and a speed; `Clip::at` gives the frame at a time and `Clip::events_between` the events between two times, by additions and comparisons only. A sheet's tags and its clips file (`.solframes`, `animation::frames_file`, read by the app beside the sheets) make a `ClipSet`; the editor works out every sheet's and clips file's set whenever one changes (`SpriteSheets::work_out_clips`) and hands them to the world each frame (`World::set_clip_sets`). Each tick, after projectiles and before game code, `World::step_sprites` moves every playing Sprite's time on by the tick times its speeds (in a fixed order, so the checksum agrees), keeps a looping clip's time within one pass, and gives back `SpriteCue`s: the editor plays a cue's sound event on the entity (`Workbench::cue_sounds`, by name) and sends it to game code as the engine's `AnimationCue` event, first in the tick's first round (`script::Game::tick_with_events`; engine events are declared in the description files from `script::describe::ENGINE_EVENTS`). Drawing shows each sprite's clip frame at its time (`SpriteSheets::shown_frame`); in the editor, plus the time since Preview animation was turned on. The Clips and Frames tabs edit a clips file (`editor::frames_editor`), save each change through the app (`WorkbenchAction::SaveFrames`) and put it into the sheets at once, so every sprite shows it; they're panels that come with an open file (`Panel::OPEN_WITH_A_FILE`) and are never saved in a layout. **Atlas Crop** ([decision 0089](docs/decisions/0089-atlas-crop-and-the-ui-editor.md)) cuts named pictures out of a sheet: `animation::atlas` reads and writes `<picture>.atlas.lst` (a Lust data file beside the picture, which never changes); the app reads atlas files with the tilesets and their pictures whole (`SpriteSheets::atlases`, `tile_art`); the Atlas Crop tab (`editor::atlas_editor`, `atlas_view`, `workbench_atlas`) comes with an open atlas like the Tileset tab, saving each change through the app (`WorkbenchAction::SaveAtlas`); and `solis/project.lst` names every crop as `Picture.<picture path>.<crop>`.

Animators (Phase 9, D3b; [decision 0066](docs/decisions/0066-animator-state-machine.md)) choose which clip a sprite plays. An animator file (`.solanim`, `animation::animator_file`, a settings file with blocks, `area::settings::read_block_settings`) holds parameters (numbers, switches, triggers, directions), states (a clip, or a clip per facing direction) and transitions (from a state or any state, with conditions that must all hold), each by a stable random ID. `animation::Animator` is a file made ready to run, and `animation::Run` one entity's state and values; the app reads the project's animators beside the sheets, and the editor makes each ready to run (`SpriteSheets::animator_set`) and hands them to the world each tick (`World::set_animators`). Each tick, before sprites move on, `World::step_animators` steps every entity with an `Animator` component: the first transition whose conditions hold is taken, triggers are put out, and its Sprite gets the state's clip (restarted on a new state; changed in place, keeping its time, when only the facing turned) and speed. Runs live beside the entity's components (`world::animators::Running`), carry over a changed file by name, and are kept over edits; their state and values are in the checksum; saves keep the state in the area and the values in their own section. The Animator tab (`editor::animator_view`) is drawn on the shared graph editor (`editor::graph_canvas`, decision 0050), which reports what was done so its user changes its own document as undo steps. Game code doesn't reach animators yet: under the API guidelines ([decision 0065](docs/decisions/0065-engine-api-guidelines.md)) the editor will write a Lust file per animator, a state of its state names and a class with a method per parameter, once Lust's natives can take states.

**Game UI** ([decision 0083](docs/decisions/0083-game-ui-on-any-screen.md), [plan](docs/plans/game-ui.md)): a `ui::Screen` is a tree of elements, each pinned to its parent by an anchor (nine points, or stretched across or down) with an offset and size in design pixels; `ui::layout` scales them by the screen's rule (grow with the screen's height, keep its size, or the game picture's whole step for pixel art, edges snapped to its pixels) into `ui::Shape`s in drawing order. `render::UiPipeline` draws them over a finished picture after tone mapping, one instance (112 bytes) per shape in one draw call, each edge worked out from its signed distance in `ui.wgsl` (hard-edged for whole steps); each shape carries the box it may be drawn in (`Shape::clip`, from an element that `clips`, as a Lust canvas's group does), and the shader drops what's outside. The editor carries a screen on `ViewportView::ui`; the app lays it out on the image's real size (inside a 2D game's picture, `ui::layout_at`, at its whole step) and draws it after the frame (`ViewportRenderer::draw_ui`, `draw_ui_on_pixels`). Text ([decision 0084](docs/decisions/0084-game-ui-text.md)): `ui::Fonts` reads fonts with `ab_glyph` and lays a `Text` element's letters out (`ui::layout_with`); each letter is made once into a single-channel distance image in a 1024 × 1024 atlas (`ui::text::Atlas`, its `revision` telling the renderer when to upload it again), and `ui.wgsl` draws a letter like any shape, its distance read from the atlas. The app keeps one `Fonts` (Inter regular and semibold). The Console's `ui test` shows a sample HUD. **Screens in Lust** ([decision 0087](docs/decisions/0087-screens-through-the-engine.md)): `assets/ui/<name>.lst` passes an assembly with a view, named after its file. `script::screens` finds them, writes an entry opening each (`solis screens.lst`) and compiles them into a program of their own beside the game's (`Compiled::screens`); `script::Screens` runs it in a `Runtime` of its own, whose `LUST_HOST.ui_open` keeps each screen's view, and reads a view's tree (`{k, t, s, c, v}`) into `ui::view::Node`s, bounded. The editor (`game_screens.rs`) starts them with the program, copies the game-wide objects in after each frame's ticks (writes to them stop the screen, as objects allow writes only in their own updates), runs the shown `Screen` components' views in order, and puts each on `ViewportView::ui` as a `ui::Screen` with its `view`; `ui::layout_with` lays a view out with Lust's rules (`ui::view`, ported from Lust's `native_ui.rs`) at the design height and the screen's shape, then draws it like elements. Screens read the entity they're shown for (M2b): `script::screens::readers_file` writes `solis/screen.lst` into the screens' compile only (`Ui` and a reading method on entities per Lust component, minus names engine calls take), and `Runtime::run_view` lends `Ui_entity` and `entity_<reader>` natives for that view, each making a copy with the program's `new` and the game's values through a `ScreenReader` (the editor's reads `script::Game::values`); a missing component is a Lua error four calls up, so it names the screen's line. The game's Lua and Rust components and Solis's own are described in the same file as Lust components of their fields (`readers_file`'s `described`, from `Compiled::schemas` and `area::builtin::registry`), and the editor's reader falls back to `World::component_data` for Solis's own; the screens' entry fetches the file so Lust knows them. Buttons (M3a, [decision 0088](docs/decisions/0088-menus-send-events.md)): a view's `{ }` comes back as a function (`f`), numbered in order (`Node::action`) and kept by `Screens` for the screen and entity; `ui::view::lay_out_with` gives each button's box (`Clickable`) and draws it hovered or focused by `ui::view::Looks`, and `ui::layout::clickable_at` finds the one at a point the same way. The Game panel says where the pointer is and where screens are laid out (`ui::layout::picture_area`, which `render::pixel_layout` uses too); `game_screens.rs` hovers the button there, and a click runs it (`Screens::press`, through `Runtime::run_action`, which lends `send_event`). What it sends waits in `GameScreens::sent` and goes into the next tick's `input::Frame::sent`, so recordings keep it (format 3) and a replay sends it again, and is delivered with the engine's events. A screen with buttons keeps the pointer free while the game has the keys. The menu keys (M3b): while such a screen is shown, `GameScreens::take_menu_keys` reads each tick's frame (sampled or replayed), moves the focus with `ui::view::next_focus` (nearest that way) and presses on MenuChoose, and leaves only `input::MENU_ACTIONS` in the frame game code sees and a recording keeps. The game's speed (M3c): `World:setGameSpeed` becomes `Change::GameSpeed`, landed by `World::set_speed`; each tick's game time is `World::tick_time` (the clock, physics, projectiles, sprites and game code's `dt`), and saves keep it (format 7). Game code's `showScreen`, `hideScreen` and `screenShown` (owner `entity`, in `solis/screens.lst`, with `state Screen` in `solis/project.lst`) become `Change::ShowScreen`, landed by `World::set_screen` on the entity's Screen in its values (in the checksum), read through `WorldView::screens`, and copied into a save's area. **The UI editor** ([decision 0089](docs/decisions/0089-atlas-crop-and-the-ui-editor.md)): a screen's file opens on the Canvas in the UI workspace (`editor::workbench_screens`). `ui::source` reads the Lust file's views into pieces with their places in the text and makes edits that change the fewest letters; `editor::screen_doc` keeps the text, undo and what's picked, and matches the file's pieces with the view the game's code makes (`script::ScreenCode::sources` gives the file, `Screens::view` the view, drawn for an entity with starting values), stopping at code that makes pieces. The canvas draws the screen through the renderer (`CANVAS_IMAGE`) and picks with `ui::layout::boxes`; each change is shown at once on the view and saved (`WorkbenchAction::SaveScreen`, `Projects::save_screen`). The tools (`editor::canvas_tools`, M5) write a new piece's Lust (`piece_text`, `pen_text`; shapes outside a `canvas` get one of their own) and put it in with `ui::source::insert_piece`. Ties (`editor::screen_ties`) list what the screen's entity can be read for from `ScreenCode::readers` and the components' schemas, and write a read at the top of the view, its fetch line and the value used (`ui::source::set_arg`, `set_style`); a button's `{ }` becomes one `send` of an event the file fetches. Preview values are numbers the canvas's `PreviewReader` gives in place of a component's starting ones, never saved. **Looks and player settings** (M6, decisions 0089 and 0091): `ui::Screen::look` (`ScreenLook`, from the Screen component in `game_screens.rs`) gives every shape without its own a glow in its own colour and an outline, and a pixel size; a piece's Lust `shadow` is its own glow (`Element::glow`). `render::UiInstance` carries them (160 bytes) and `ui.wgsl` grows each quad by them and works each block of a pixel size out at its middle, in the same draw call. `script::settings::PlayerSettings` (text size, UI size, fullscreen, window size) is the player's, not game state: `WorldView::settings` shows it to game code, `Change::Setting` lands in the editor's `ViewCache` and is kept on `Workbench::player_settings` from play to play; screens read it through `ScreenReader::settings`. Text size is `ui::view::Looks::text_percent` (every text's `size` grows as it's laid out); UI size multiplies the screen's scale (`ui::layout::screen_scale`). The UI sample (`app::ui_sample`, M7) is made from `samples/ui/assets`, like the turret sample. **Day and night** ([decision 0092](docs/decisions/0092-day-and-night-and-lamps-on-sprites.md)): the Environment's day (length, start, `area::builtin::DayColours` stops written as text and edited by `editor::day_colours` through `Offer::DayColours`) and `World::time_of_day` (game time plus the hours `World:setTimeOfDay` moved it on, `World::day_shift`, kept in saves' `day` section and the checksum). `AreaView::hour` and `ViewportView::hour` carry the hour (the viewport's `preview_hour` while editing); the app turns it into `render::Environment::tint` and leaves out `only_at_night` lamps by day (`ViewportView::lamps_shining`). `FrameUniforms` tints the sun and the sky's light, and `sprite_light` lets `sprite_fs` light each sprite pixel by the tint and the lamps shining down on the ground there, in optional steps. **Pictures on screens** ([decision 0089](docs/decisions/0089-atlas-crop-and-the-ui-editor.md)): Lust's `image "sprites/tools.png#Axe"` names a picture and, after `#`, an Atlas Crop crop. `script::screens::pictures_named` finds the names written out in screens' code (`ScreenCode::pictures`); the editor (`screen_pictures.rs`) adds those seen as screens run, asks the app to read the files (`Workbench::take_wanted_pictures`, `app::sprites::Sprites::want_pictures`, into `SpriteSheets::tile_art`), cuts crops by `SpriteSheets::atlases`, packs them all into one `ui::Pictures` (2048 × 2048, premultiplied, an edge pixel copied round each) shared by every `ui::Screen`, and lists a written name that can't be shown in Problems at its line. `ui::layout` makes a `ShapeKind::Picture` from its part of the atlas; `render::UiPipeline` uploads the atlas when its revision changes and `ui.wgsl` reads it, a whole pixel at a time when shown bigger (`Shape::blocky`), else smoothed.

**What Solis makes is Lust** ([decision 0081](docs/decisions/0081-what-solis-makes-is-lust.md)): each file Solis makes is moving to a Lust data file named for what it holds, `<name>.<kind>.lst` (`reflect::data_files` is the one list of kinds; the asset database and Library know a file's kind from it, and the game code gatherer leaves such files out of the program). A data file fetches its classes from `solis/data/<kind>` (written with the engine's other files, `script::describe::DATA_CLASSES`), says `lock int version = N;`, and holds only `lock` values of fixed values; `area::lust_data` writes them (an `f32` as its own shortest text) and reads them with `lust::read_values_with`, handing Lust the classes itself, so nothing runs and every type and option is checked. Formats made of settings blocks share `write_blocks`/`read_blocks`, which keep the older layout's blocks as Lust things and read them back into the same blocks, so each format's checks read either layout. When a project opens, `app::to_lust` moves each older file: written as Lust beside it, checked, its sidecar moved (`asset_db::backup::move_to_new_format`), the older file kept in the backups. Tile maps (version 3, `tiles::map_lust`) and tilesets (version 4) are the first; [docs/plans/lust-data.md](docs/plans/lust-data.md) lists the rest.

Tile maps (Phase 9, D4; [decision 0067](docs/decisions/0067-tile-maps.md)) are the `tiles` crate. A `Tileset` (`.tileset.lst`, `tiles::tileset`) lists terrains, each with a stable ID, a name, a one-character code and a colour. A `TileMap` (`.tilemap.lst`, `tiles::map_file`) is a size, its tileset's asset ID, layers (each a byte per cell holding a terrain's code, 0 for empty, under or over sprites) and values (each a column of numbers, switches or choices). The cells are `Arc`'d per layer and column, so copies share them until changed. A change marks its 32 × 32 chunk dirty, and the checksum is worked out again only for dirty chunks. Both files are block settings files (`area::settings::read_block_settings_within`, which caps the blocks read): a map's chunks are blocks of rows of codes, and its values blocks of only the cells not at their start. The app reads tilesets and maps beside the sheets (`app::sprites`); the editor keeps them in `SpriteSheets` (`tilesets`, `tile_maps`, and `map_set` by asset ID for the world). A `TileMap` component on an entity places a map: `World::set_tile_maps` and `World::start_maps` (each tick, before animators) give each such entity its own copy (`world::tile_maps::MapState`), started again when its file changes and kept over edits. Copies are in the checksum (`World::map_sums`) and saves (`solis save 5`, a `tilemaps` section of each map's own file text, put back by `World::restore_tile_maps`). The editor draws each layer as one quad whose picture has a texel per cell in its terrains' colours (`editor::tile_view::TilePictures`, made again only when a layer's cells, its revision or the tileset change; the app uploads a picture when its key changes). The renderer draws layers under sprites first, with depth ignored, and layers over sprites last (`render::SpriteLayer::Under` and `Over`, a flat pipeline); picking leaves them out. While a map is selected, the Map tab (`editor::map_tab`, beside Properties) changes the map file through `Workbench::change_map`, one undo step each, saved at once. The viewport lays the overlay over the map (`tile_view::draw_overlay`: values, chunks, the hovered cell), with its menu kept out of the view's presses. Game code reaches a map through its own Lust file (`script::map_code`, decision 0079), written beside the animators' into `solis/maps/`; it reads `WorldView::maps` (the maps at play as the tick started, made again only when `World::maps_revision` moves) and its changes land at the end of the tick on the first entity showing that file (`World::set_tile`, `World::set_cell_value`). Where each map lies (`script::MapPlace`: its entity's transform, the tile size in metres, its size in cells; decision 0082) is worked out by the editor every tick into `WorldView::map_places` and `map_bounds`, so `cellAt`, `placeOf` and `entity:mapBounds()` follow a map that game code moved; `WorldView::view_size` is the 2D view in metres, which the kit's `FollowCamera2D` keeps inside a map's box.

Tile art (Phase 9, D5; [decision 0068](docs/decisions/0068-tile-art-and-autotiling.md)) adds to a tileset (version 2) a picture (a PNG, JPEG or Aseprite asset; pictures now have IDs, `asset_db::AssetKind::Picture`), a tile size, a kind per terrain, pieces (a tile of the picture filling a slot, with a weight and an animation) and rules. `tiles::autotile` is pure arithmetic: `chunk_tiles` gives a chunk's tiles of one layer as `Placed` (in half cells, so a 16-tile piece sits where four cells meet; a pass, so later terrains lie over earlier; `Art::Piece`, `Missing` or `Colour`), variations picked by `pick` from a hash of the place. The app reads each tileset's picture whole (`assets::tile_art`, `app::sprites::read_art`) into `SpriteSheets::tile_art`. `editor::tile_view::TilePictures::draw` takes the part of the ground in view (`ground_in_view`, from the view's projection) and the time: for a map with art it autotiles only the chunks in view, each kept until it or a chunk beside it changes (`TileMap::chunk_revision`), and draws them as sprites from one atlas per picture (`atlas_rgba`: the frames stacked, then a white patch tinted for colours and pink); past `MOST_CHUNKS` in view it draws D4's colour pictures. The Tileset tab (`editor::tileset_view`, state in `tileset_editor`, workbench side in `workbench_tileset`) edits the open tileset as undo steps, saved at once (`SaveTileset`), and saves templates as new PNGs (`WorkbenchAction::SavePicture`). `SpriteSheets::tile_gaps` feeds Problems' `MissingTiles`.

The tile painter (Phase 9, D6; [decision 0069](docs/decisions/0069-the-tile-painter.md)) is the editor's, its shapes the `tiles` crate's (`tiles::paint`: a line's cells, a rectangle clipped to the map, a fill's reach, a `Stamp` copied, flipped and turned). While a map is selected, `editor::tile_paint` puts the painting tools on the viewport's tool bar and keeps their settings in `TileOverlay::paint`; the viewport hands each frame's buttons and the cell under the pointer to the workbench (`workbench_paint.rs`) instead of picking, and leaves right-drag and flying alone. A stroke paints the map file's own copy (`TileMap` layers are shared until changed), swapped into `SpriteSheets` each frame so the viewport draws it at once and autotiles only the chunks it touched; when the button comes up it's one undo step with the Map tab's and the file is written once. Exact tiles (`TileMap::set_exact`) are cells showing one piece as it is: art only, not in the checksum, kept per chunk in tile map files version 2 (an upgrader from 1). A frame of brushing on a 1,000 × 1,000 map with art takes about 1 ms (`scale_check_painting_a_1000_by_1000_map`).

## Play mode

Play keeps a copy of the `Document` (area, history, selection) and of the assemblies, and builds a `world::World` from the area: the same entities in `hecs` ([decision 0024](docs/decisions/0024-game-storage-is-hecs.md)). Each frame the workbench steps it and takes in what changed: the document notes which entities each edit touched (`Document::take_changes`), and the world updates only those (`World::update`), or builds itself again when entities were added, deleted or reparented, or after an undo or redo. **The fixed step:** the world moves on in ticks of 1/60 s (`world::TICK`), at most 8 a frame (`World::due`), whatever the frame rate, so a game plays the same at any frame rate; the clock moves on as each tick begins (`World::begin_tick`), so a frame that stops early never counts ticks that didn't run; Step runs one while paused. Each tick runs in this order (`Workbench::run_game`): land what game code spawned and despawned before it (`land_edits`), remember where everything is (`World::remember`), move projectiles, game code's game-wide objects' updates (on the first shard, their values then copied to the others; only those updates may change them, guarded in Luau by `script::objects`, decision 0080), its updates and rounds of events (each phase's changes landed at its end, decision 0033), then land what the tick spawned and despawned (a `setSeed` from this tick holds only after it, so the starts it ran see the old seed, as any later tick's would), then physics, then game code's saves and loads (each slot once a tick, at most `MAX_SAVES_PER_TICK`; what the starts of newly landed entities spawned in turn lands first, up to 8 rounds, so a save holds it; made before a pause stops the frame; a replay makes each save too, since saving builds physics again and the recorded play did, but doesn't write it; `editor::save_game`, decision 0038: a save is the area as the editor has it (copies of assemblies kept as plain entities) and, apart, where the game has moved each entity (the world keeps the two apart, so an edit while playing starts from the editor's place in a loaded game too), every running component's values, the game-wide objects' values (an `objects` section, `solis save 6`), the input actions, projectiles and each body's place and motion (never Rapier's insides), in sections of a text file with a checksum; saving builds the running game's physics again from those body states and loading builds the loaded game's from them (`World::rebuild_physics`, every entity joining in ID order), so the two carry on exactly alike and nothing in a file reaches Rapier; loading then starts game code and gives the running components their saved values, only for components the saved area has on each entity; a load ends the frame's ticks. Saves are written, and loads read and built, on the frame: a big game's save or load is a pause (a worker would hide it; noted for later), and game code can save each slot once a tick, so the saves folder's total cap is what stops a game filling the disk). Physics is `World::step_physics`: bodies follow what game code moved, its pushes and velocities are made in the order game code asked, then its character moves (`walk`, Rapier's character controller; worked out on every core at once, made in the order asked; Solis keeps a grounded character to the ground itself and carries it with the kinematic body under its feet, since Rapier does neither the way Solis needs), Rapier steps, and the entities physics moved (awake dynamic bodies, and characters whose move went somewhere) follow their bodies). **Ready-made components** (Phase 6, M5): the character controller and the cameras are Lust (`script::describe::KIT`), written into every project's `solis/kit/` beside the natives' descriptions, so they're game code like any other: deterministic, saved, swapped, and readable by game makers. **Physics** ([decision 0036](docs/decisions/0036-physics-is-rapier-strict-on-every-pc.md)) is the `physics` crate: Rapier in its strict mode, wrapped so games and the rest of Solis never meet it. The world makes a body and collider for each entity with a `RigidBody` or `Collider` (built-in components in `area`), and a character (a kinematic capsule, `Physics::add_character`) for each with a `CharacterBody`, keeps them as entities join, leave and change, and shares the physics state (`Arc<physics::State>`) with game code's view, so `velocityOf` and `castRay` read it on every core; it changes only between phases, so usually without a copy. **2D physics** ([decision 0071](docs/decisions/0071-2d-physics-and-top-down-movement.md)) is a world of its own, `physics::flat` (Rapier2D in its strict mode): entities with a `Collider2D` (pixels, turned into metres with the project's 2D settings) join it, and each tile map's solid cells (a tileset's `solid` terrains) become walls, merged into rectangles per 32 × 32 chunk (`tiles::walls`) and built again only where cells changed (`world::flat_physics`). `step_physics` steps it first: walls catch up, then 2D characters take game code's `walk` moves in the order asked with Solis's own mover (cast, a skin back out, slide), which never catches on the seams between walls; entities follow on the ground at their own layer. Game code's view holds its state (`WorldView::flat`). It's in the checksum, and built again from entities and maps rather than saved. **Determinism:** random numbers are made from the game's seed and the place in the tick's order they were asked for (`script::game::random_from`), not drawn in turn, so any number of cores gives the same ones; `World::checksum` (entities, places, values, projectiles, physics, the seed; not the clock, which during a frame of several ticks has moved on by all of them; which entities, their tree, names and component values are hashed once per revision, since only the area changes them) and `Game::checksum` (game code's running values) compare two runs tick by tick. The Game panel draws an `AreaView` made from the world (`AreaView::of_world`), each entity drawn part way between the last tick and now by `World::progress` (`World::placed_between`), so screens faster than 60 Hz show smooth movement, through the first camera, into its own image (`ViewportView::image`; the app keeps one render target per image) with `editor_lines` off, so no grid, axes or lamp markers. Stop puts the copy back, but first notes the edits made while playing (`History::labels_since` the state at Play): if there are any, they wait as a `PlayChanges` (the edited document) for **Keep** (swapped back in, history and all) or **Undo all** ([decision 0085](docs/decisions/0085-the-editor-overhaul.md); a modal question; Play and the editor's keys wait meanwhile), and while the game runs the window's edge and its top and status bars take the play colour (closing the window while playing asks about unsaved changes to that copy first, and stops only once it closes); assemblies changed on disk meanwhile rebuild their copies again, and an area file changed on disk is offered again. Actions that save or replace the area are refused while playing, with a message (`play::waits_for_stop`), and results of Open and Save windows opened before Play wait until Stop.

**Exported games** ([decision 0093](docs/decisions/0093-the-playtest-export.md)): the playtest export is the same program, renamed after the game. `main.rs` first looks beside the program for `playtest.txt` (`app::playtest::beside`); finding one, it runs `window::run_playtest` instead of the editor. That is `App` with no splash, no update check and no launcher, whose frame (`window_playtest.rs`) opens the project in `game/`, opens the area, and plays it once `GameCode` has a program (`Workbench::start_play_only`). `Workbench::show_play_only` (`editor::play_only`) runs the game and draws only the Game panel's picture, filling the window; Esc is the game's, and losing focus keeps the keys. The player's settings drive real `ViewportCommand`s (fullscreen, the window's size in pixels over the scale) and are kept in `settings.txt` in `app::playtest::saved_games` (`Saved Games/<Game>`), where saves, `log.txt` (the Console's warnings and errors) and, from a panic hook, `crash log.txt` go too. `Window:quit()` is `Change::Quit`: `ViewCache::quit` ends the frame's ticks and stops play, and in an exported game `Workbench::quit_asked` makes it `WorkbenchAction::Quit`. File > Export for playtesting… (`editor::export_dialog`) sends `WorkbenchAction::ExportPlaytest`; `app::playtest::export` copies the program and the project (leaving out the cache, builds, saves, recordings, backups, `.git` and links) into a new or empty folder outside the project, on a thread, and the project remembers the choice in `.solis/last export.txt`.

## Area files

An area is saved as a `.solarea` text file: `area::text::write` and `read` turn an `Area` into Lust-style blocks and back, made to merge in Git ([decision 0020](docs/decisions/0020-scene-files-in-lust-style.md)). The editor never touches files: it asks (`SaveArea`, `OpenArea`…) and the app (`crates/app/src/area_file.rs`) shows the system's windows, writes through a temporary file and a swap, and checks the open file once a second for changes made elsewhere, which the editor loads as one undoable step. `area::History::state` tells whether there are unsaved changes: it comes back to the saved value when undo or redo return to the save.

## File formats and upgrades

Every file format a project holds has a version and a chain of upgraders (Phase 8, C1; [decision 0053](docs/decisions/0053-compatibility-before-2d.md)), through one shared path, `reflect::upgrade::Format<T>`: `current`, a cheap `version_of(text)`, and `steps`, where `steps[0]` turns version 1 into 2. Each reader reads the file as written into its own unchecked form (an area's `AreaFile`, a settings file's fields, a TOML table, a `Recording`), runs `Format::upgrade` from the file's version, and only then checks and uses it; a newer file is refused before it's read on. The formats: `area::text::FORMAT` (areas and assemblies), `sound::event::FORMAT`, `sound::mixer::FORMAT`, `input::BINDINGS_FORMAT` (format 2: version 1 had no version line and wrote `ArrowUp`), `input::RECORDING_FORMAT`, `asset_db::PROJECT_FORMAT`, `asset_db::SIDECAR_FORMAT` and the editor's save games (`save_game::FORMAT`, C2: a save's sections are read as written, upgraded, then read; version 1's physics, Rapier's own bytes, is dropped with a note, so bodies start at rest; version 2 kept the game's places in the area, which loads the same with none apart; versions before 3 may carry a checksum of the body alone). A save's areas and input actions go through their own formats' upgraders as they're read. A save is never refused for being older.

The file on disk isn't touched until it's saved. Saving goes through `asset_db::backup::save` (in the app, `app::upgrades::save`): when the file on disk isn't in the current format, the new text must read back and write out as itself, the old file is copied to `.solis/backups/<date and time>/<its path in the project>` (folders made with `own_folder`, never through a link) and checked, and only then is the new file swapped in and checked on disk; any failure leaves the old file. A file already current is simply written atomically. `backup::trim` removes backups over 90 days old or past 1 GB in all, never the newest. The app notes an upgraded file in the Console on opening (`upgrades::older_note`) and where its copy went on saving (`kept_note`).

`tests/fixtures/<format>/v<N>/` keeps a file of every version of every format ever released; `crates/app/src/fixtures_tests.rs` opens each with the current build, checks its version, and fails if a format's version went up without an example of the old one, or if a step is missing (`Format::is_complete`).

## The game-code interface

What game code can call is guarded (Phase 8, C3; decision 0053). `script::interface::snapshot` lists it as text: every native's Lust (`describe::NATIVES`), the names lent to Lua's `solis` (read from `host.rs`'s `natives.raw_set` calls), the methods of `Host`, `RustComponent` and `Context`, renamed natives, and the ready-made components with their fields. A test compares it with `docs/game-code-interface.txt` and fails, listing the lines, when they differ. A deliberate rename adds a `describe::Renamed` line: the old name is described in `solis/<file>.lst` and lent to Lust and Lua as the same function (`host::lend_old_names`), and `script::renamed_uses` finds each use in the project's Lust and Lua (outside comments) for the Problems panel, as a warning saying the new name and until when.

## Checking a project

`solis --check-project <folder>` (`app::check_project`, Phase 8, C4) opens a project as a new build would, without a window: it reads every file Solis reads (by extension, through each format's reader, so older files are upgraded and noted), checks the game's code (`GameCode::describe`, `script::gather`, `compile`, `renamed_uses`), and plays back each recording in `recordings/checks/`. Recordings name their area since format 2 (`input::Recording::area`, inside the assets); `check_project::workbench_for` builds a headless `editor::Workbench` with the project's code, Rust components, input actions, every assembly and the Library, opens that area and replays the recording with `Workbench::play_for`, reading the outcome from `Workbench::replayed`. The report is printed and written to `.solis/check-report.txt`; the program exits 1 if anything failed. `check_project_tests::the_samples_check_out` makes the turret sample, the benchmark and the playground and checks each, so every pull request checks the samples.

## Assemblies

An assembly is a `.solassembly` file (the area format with one root). In an area it's written as the copy's root entity naming the assembly plus overrides (`root/inner` blocks with only what differs); while edited, copies are ordinary entities carrying an `Origin` (assembly, copy root, path inside), with IDs worked out from the copy's root and the path (`area::assembly::derive`), so the same file always expands to the same IDs ([decision 0020](docs/decisions/0020-scene-files-in-lust-style.md)). `area::assembly::Expander` expands on opening and collapses on saving, comparing each copy with its assembly. The editor holds the assembly files (`Workbench::set_assembly`); when one changes, every copy is collapsed against the old contents and expanded against the new, so its changes survive. A placed model is one entity; Unpack splits it into entities that each draw one node (`render::Placement::node`).
