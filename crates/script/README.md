# script

**Layer 1 · Engine**

Game code ([decision 0028](../../docs/decisions/0028-lust-runs-as-luau-while-editing.md)): a project's Lust, checked and turned into Lua by the Lust compiler (used as a library), and its Lua components, run together in Luau while the game plays.

## Purpose

- **The engine described to Lust** (`describe.rs`, [decision 0016](../../docs/decisions/0016-how-lust-joins-solis.md)): `NATIVES` lists every native method Solis gives game code. `descriptions` turns it into the Lust files a project gets in `assets/solis/` (`world.lst`, `entity.lst`, `physics.lst`, `input.lst`, `sound.lst`, `animation.lst`, `tiles.lst`, `screens.lst` and `window.lst`), so they always match the engine, plus the ready-made components (`KIT`, from `src/kit/`): `kit/character.lst` (CharacterController), `kit/topdown.lst` (TopDownController, decision 0071) and `kit/cameras.lst` (ThirdPersonCamera, FirstPersonCamera, RtsCamera), Lust a game fetches and uses or copies.
- **Methods on things, and the project's names** (decision 0073): each `Native` has an `owner`: `"entity"` for an entity's abilities (`method vec3 entity:position() native;`, called bare inside a component), an engine object's name (`World`, `Saves`, written as `object World { … }`), or none. Its body's key in `LUST_NATIVES` is `Native::key` (`entity_position`, `World_say`); Lua reaches them as `solis.entity.position(e)` and `solis.World:say(w)`. `solis` has a group for every owner a native has (`describe::owners`, handed to the prelude as each Luau is made, never a list kept by hand), so a new engine object is within Lua's reach as soon as it has a native. `project_names.rs` writes `solis/project.lst`, the project's names as states (its assemblies, input actions, sound events, buses, clips and cues, screens and Atlas Crop's pictures: `Assembly.Ships.Fighter`, `Action.Jump`, `Sound.Sfx.Footstep`, `Bus.Music`), and turns an option back into the file's path (`path_of`). Sound is `Audio:play`, `Audio:playAt`, `Audio:setVolume` and the entity's `playSound`, `stopSounds` and `setSoundPlaying` (decision 0076); clips are the entity's `animate`, `animateFromStart`, `stopAnimation` and `setFlip` (mirroring its Sprite, `Change::Flip`), and the engine's `CueReached` and `ClipFinished` events carry `Cue` and `Clip` (decision 0077). `animator_code.rs` writes each animator's own Lust file (`solis/animators/…`: a state of its states, a class with a method per parameter calling the `Animators` object by the graph's names); a component's field of that class is filled in by `syncing::make_lust` with `make` (decision 0078). `map_code.rs` does the same for each tile map (`solis/maps/…`: states of its layers, terrains and choices, a class calling the `Maps` object), read from `WorldView::maps` and changed through `Change::MapTile` and `Change::MapValue` (decision 0079). Game-wide objects (decision 0080): `objects.rs` reads the Lust's passed objects (`objectNames`), moves each one's fields into a store its metatable guards (written only while `Objects::open` runs their updates), and reads and writes their kept fields; `Ticking::objects` runs their updates before the components, and `Game` runs them on the first shard (`Job::Objects`) and copies their values to the others (`Job::SetObjects`), with `object_values`, `set_object_values` and `object_info` for saves and the editor. Cells at places (decision 0082): a map's class has `cellAt` and `placeOf` (`Maps:cellAt`, `Maps:placeOf`, worked out by `MapPlace` from `WorldView::map_places`), `entity:mapBounds()` reads `WorldView::map_bounds` and `World:viewSize()` `WorldView::view_size`; the kit's `FollowCamera2D` uses them. Screens (decisions 0087 and 0088): `screens.rs` compiles and runs the game's screens, describing the game's Lua and Rust components and Solis's own to them as Lust components of their fields (`readers_file`); a view's tree is game code's and is read after its time limit has ended, so it's read within one budget for the whole view (`MAX_PIECES` pieces, `MAX_STYLES` styles, `MAX_VIEW_BYTES` of text, each text cut to 16 KB before it's copied; anything in a list counts, and a table used many times is counted each time): pieces past the most are left out, and past the other two the view fails with a plain message; a button's `{ }` runs through `Screens::press`, giving back the events it sent; game code's `showScreen`, `hideScreen` and `screenShown` (in `solis/screens.lst`, taking `state Screen`) become `Change::ShowScreen` and read `WorldView::screens`. `MOVED` lists the calls that changed shape: Lust's "there's no method called positionOf" becomes a mistake saying the new way, and Lua's `solis.positionOf` is found before it runs.
- **A project's code** (`code.rs`): `gather` reads every `.lst` and `.lua` file in the assets within limits (1 MB a file, 16 MB and 10,000 files in all, hidden folders skipped). `check` runs Lust's checker from `main.lst` (with the engine's folder as Lust's host folder, `describe::engine_folders`: the branding's `area::lust_data::ENGINE_FOLDER`, the one rule for which files are the engine's, `describe::in_engine_folder`, that the screens and the screen editor use too; decisions 0072 and 0110) and gives back every mistake as a `CodeProblem` with file, line and column. `compile` also starts the code on its own (no world) to read its components' schemas into `Compiled::schemas` (and where each is written, `Compiled::places`), so the editor never runs it on the frame. The start's `send`s go nowhere, and the natives are lent while it and the starting values run. Lust itself refuses code nested more than 150 levels deep (brackets, blocks, operators in a row) and runs on a stack of its own (2.0.0-alpha.67, decision 0106); `compile` also runs on a thread with a 64 MB stack, for Luau compiling what Lust made. A `vec3` is a Luau vector in Luau, in Lust and Lua alike (Lust's `vectors` must say `"luau"`, checked at load). Both are meant for a worker thread. Checks take turns (`check_turns.rs`): the Lust compiler can't be stopped, so a check that runs past `COMPILE_LIMIT` (30 s) is given up on with its thread kept, and no other check starts until that thread ends: `compile` then gives one mistake saying which check never finished and which files changed since, and `try_compile` says it apart (`Err(NotStarted)`) so the editor checks again once `check_unfinished` says it has ended. One check runs at a time in the whole program, so at most one given-up check is ever running, in the editor, an exported game and `--check-project` alike. Before compiling, `long_prefix_chains` refuses long runs of `!` and `shared_names` two classes, objects, components, nodes or schemas with one name, which the pinned Lust (alpha 67, as alpha 59) takes minutes over or never finishes (`area::lust_guard` finds both).
- **Speed:** the interrupt that keeps the time limit reads the clock once in 32 interrupts; each Lust component's `update` and `handle` are looked up once when the code loads (Lust's classes don't change while it runs; Lua's can, so they're looked up each time); an event's `on_` name and its values for Lust are made once for every component it reaches; vectors handed to game code are pre-sized tables.
- **On every core** (`game.rs`, [decision 0033](../../docs/decisions/0033-game-code-sees-the-start-of-the-tick.md)): a `Game` holds one `Runtime` per shard, each with its own Luau, the same code and the entities whose ID falls to it (the ID mixed with splitmix64's finalizer, modulo the shard count: spawned IDs are all odd, so the raw ID would leave shards idle). The first shard runs on the caller's thread, working while the others do; more run on threads of their own, sent jobs over channels. Loading and swapping are all or none: a shard that fails takes every shard back (unloaded, or the last code swapped in again). `len` is counted once until components are added, removed or the code changes. During a tick each phase (the updates, then each round of events) reads a `WorldView` made at its start (places, names, the time) plus the component's own changes, and keeps what it writes (`Change::Move`, `Change::Turn`, said lines, sent events) with an `Order` (entity ID, or the event's number, then component name and sequence); the `Game` sorts them and lands them in the `GameWorld` at the phase's end. So the same game gives the same world, Console and events on 1 shard or 32. `Game` offers what `Runtime` does (`load`, `swap`, `sync_many`, `retain_only`, `retain_on` for many entities in one trip, `values`, `tick`); time limits, the tick budget and failures work per shard.
- **The sandbox** (`luau.rs`): one Luau per `Runtime`, with a 64 MB memory limit and deadlines: 100 ms per call, 250 ms for all of a tick on one shard (`TICK_LIMIT`: past it the tick is cut short and `Ticked::pause` asks the editor to pause), 1 s for all of a load's starts (`LOAD_LIMIT`; compiling isn't counted). The deadlines are kept on the real clock, so a thread the machine keeps off the processor uses them up while running nothing; a game always has them (`Limits::default`), and tests that compare one run of a game with another give theirs an hour instead (`Limits::unhurried`, through `Game::set_limits` and `code::compile_within`), so a busy machine can't cut a tick short and make the two runs differ; a test of one limit gives the others an hour, so only that one is tried (`Limits::calls_unhurried`). Other crates' tests reach the same through `test_support` (`unhurried`, `calls_unhurried`, `compile_unhurried`), built only with the `test-support` feature, which only a dev-dependency turns on (the editor's): never in a build of Solis. Every place Solis touches game code's tables runs under a deadline or reads and writes raw, so no metatable can hang it. Luau's `package` library isn't given (its `require` would read and run `.lua` files from anywhere on disk), and game code's text is always loaded as text (`luau::as_text`): Luau would take text starting with a byte below 0x09 for compiled bytecode, whose loader isn't made for hostile files; only bytecode Solis's own worker made is loaded as such. The libraries and the prelude (`component`, `vec3`, `solis`) are read-only, and the Lust and each Lua file get globals of their own that fall through to them. `LUST_NATIVES` lives in the Lust's globals; `solis` reaches the natives through a function only Solis holds.
- **Running components** (`runtime.rs`): a `Runtime` loads the Lua in that Luau, from the Luau bytecode `compile` made on the worker (`Compiled::bytecode`) when it has it, so loading on the frame skips compiling. It reads each component's fields into a `reflect` schema (starting values from a fresh component), makes and syncs running components from the area's values (`sync` sends only fields that changed, so values the game changed are kept, and does nothing at all when nothing did; `sync_many` does a batch with the natives lent once, in `syncing.rs`; `Game::sync_edited` is `sync_many` with the fields set by hand since the last one, which a running component is given even when the area's value is what it was, since the game may have changed its own; `retain_on` stops one entity's components), and runs ticks: the tweens game code started first (Lust's `tickTweens`, once a tick on each shard, after the game-wide objects, which stay closed to tweens; a tween's failure is said once until the code changes; decision 0106), then entities in ID order, components in name order. The native methods reach the game through a `Host`, lent once per tick in a `LUST_NATIVES` table that exists only while game code runs. A component that fails stops alone, and its failure points at the Lust (`Failure`). `runtime.rs` keeps the runtime itself; `host.rs` the `Host` and lending the natives, which are in `natives/`, a file per engine object; `convert.rs` values between `reflect` and Luau: a `vec2` is `FieldKind::Vec2` and a `{ x, y }` table, a `colour` is `FieldKind::Color` and a `{ r, g, b, a }` table, its see-through kept as a fourth number when it isn't 1 (`reflect::Value::colour`).
- **New code while running** (`Runtime::swap`): the new chunk is loaded into the same Luau and each running Lust component gets its code in place (Lust's `swap`), keeping field values by name; what changed and what started over come back as `Swapped`. If the new code's start fails, the old keeps running; if giving the running components the new code fails partway, they all start again from the area's values, with a note.
- **Events** (`events.rs`): Lust's `send` and Rust components queue an `Event`; after each tick's updates (and the moves they made) the events are delivered in rounds, in the order sent, to each component on the entity in name order; events sent in a round make the next round, cut off after `MAX_DELIVERIES` (10,000) in a tick (said once until the code changes). At most `MAX_WAITING` events wait at once, holding at most `MAX_WAITING_BYTES` of text: past that a Lua or Lust `send` fails, and `Context::send` returns false. A `send` from Lua or Rust is checked against what the Lust declares the event carries: a wrong one isn't sent, and the sender is named (Lua: an error in it; Rust: `Context::send` returns false, and the Console says why, once). Numbers in an event no Lust declares are floats. A failure handling an event is reported once per component until the code changes, and leaves it running. What game code sends while it starts goes nowhere, by one rule on every path: the code's own start (`compile`, `load`, `swap`) and a field's starting value, when its component is made (`sync_many`, so a load of a save game too) or new code gives a running one a new field (`swap`). So nothing waits in the queue between ticks, and whatever waits during one was sent by the component that just ran. What game code says is cut to `MAX_SAID_BYTES` a line and `MAX_SAID_LINES` a tick.
- **Limits on what's kept** (`MAX_KEPT`, `MAX_SPAWN_BYTES`): kept changes live outside Luau's memory limit, so each shard keeps at most 200,000 changes and lines and 4 MB of spawned assembly names a phase; past them they're dropped, and the `Game` says so once (until the code changes). At most `MAX_SHARDS` (16) shards. The time limit is sticky: once a call is past its deadline every interrupt raises, so `pcall` in a loop can't hold it off.
- **Spawning** (`spawn(file, place)`, `despawn(entity)`, `frameTime()` in `solis/world.lst`; [decision 0035](../../docs/decisions/0035-game-code-spawns-into-the-area-while-playing.md)): on several cores `spawn` gives back an ID made from the tick's number (`WorldView::tick`) and its place in the tick's order (FNV-1a, so the same on any number of shards; the tick's number and not the game's time, which stands still at game speed 0 while game code goes on) and keeps `Change::Spawn`; `despawn` keeps `Change::Despawn`; the host makes them. `frameTime` reads `WorldView::frame_time`.
- **Randomness** (`random`, `randomRange`, `randomInt`, `setSeed` in `solis/world.lst`; Phase 6): each number is made from `WorldView::seed`, the tick's number (`WorldView::tick`, which goes up whatever the game's speed, so a paused game doesn't roll one number over and over) and the call's place in the tick's order (`random_from`: FNV-1a then splitmix64), not drawn in turn, so it's the same on any number of shards; `setSeed` keeps `Change::Seed`. The prelude replaces Lua's `math.random` and `math.randomseed` with the same.
- **Physics** (`solis/physics.lst`: the entity's `push`, `velocity`, `setVelocity`, `walk` and `grounded`, and `Physics:castRay`, which gives back a `RayHit` (`describe::ENGINE_CLASSES`, decision 0075); decision 0036): reads go to `WorldView::physics` (the shared `physics::State` as the phase started; a component sees its own `setVelocity` at once), writes keep `Change::Push`, `Change::Velocity` and `Change::Character`. `facingAlong` (in `solis/entity.lst`) turns a direction into an upright rotation (`host::facing_along`). A ray's three answers are three natives, since Lust gives back one value.
- **Input** (`Input` in `solis/input.lst`: `held`, `pressed`, `released`, `axis`, `binding`, `rebind`, taking an `Action` from `solis/project.lst`; decisions 0037 and 0074): reads go to `WorldView::input` (the tick's `input::Frame`, the same on every core) and `WorldView::bindings`; `rebind` keeps `Change::Rebind`, which the editor makes after the tick.
- **Save games** (`Saves:saveTo`, `Saves:loadFrom` in `solis/world.lst`; decision 0038): keep `Change::Save` and `Change::Load` for the editor, for slots `valid_slot` allows (they become file names); `Game::all_values` gives every running component's values for a save.
- **Checksums:** `Game::checksum` adds up each running component's checksum (its entity, name, whether it stopped, and its values; `reflect::Checksum`), so any number of shards gives the same sum.
- **The time limits' interrupt** (`interrupt.rs`, [decision 0034](../../docs/decisions/0034-a-raw-interrupt-for-the-time-limits.md)): set on Luau directly, not through mlua (whose wrapper cost a fifth of game code's time): it finds the running clock through a thread-local that `Clock::limited` sets while a call runs (`Watching`), and raises the clock's error. The only module where Solis's own code may be `unsafe`.
- **Firing** (`World:fire` in `solis/world.lst`, `solis.World:fire` in Lua, `Host::fire` from Rust): a `Shot` the host is given; on several cores it's kept as `Change::Fire` and landed in order with the moves.
- **Left out** (`Runtime::leave_out`): Lust and Lua components the editor refused (their name is one of the engine's own, or a Rust component's) don't run; a Rust component of that name does.
- **Lua components** (`lua_components.rs`): every `.lua` file in the assets is syntax-checked on the worker (`compile`), then run in the same Luau; `component(name, fields)` makes a class (fields in order, with kinds and starting values), `solis.` reaches the natives and `solis.send` sends events, `on_Name` functions handle them, and `vec3` makes vectors that add and scale. They tick, handle events and swap like Lust's (`swap_classes`). A field can't be called `me`, `update`, `on_…` or `__…`, which would hide the entity or a method. A mistake with one of Solis's calls is said for someone new to game engines, with the file and line of their own code (`lua_problem`, which takes the place from the calls that led to the error when its first line names none: a native's error, `error(msg, 0)`, the time limit): a native taking several values reads each by itself (`native_values::native`), so one of the wrong kind names the call and the value (`solis.World:say(words) wants text for words, and was given nothing (nil)`), and a native kept in a variable past the moment it was lent for says what to write instead (`KEPT`). The Lua library's own words for either never reach the author.
- **Rust components** (`rust_component.rs`): a game's `RustComponent`, made from a `RustKind` (schema and constructor), runs in the same ticks and order and sends and handles the same events through a `Context`. A panic in one (making it, updating it, giving it changes, reading its values) is caught and stops only it.

## Must never

- Crash on any code, however damaged: a panic inside the compiler is caught and reported as a mistake (fuzz-tested).
- Read files beyond its limits, or follow links to folders (they could loop).
- Leave more than one check of the code running after giving up on it, or start a check while one is.
- Let game code reach files, programs or the network (Luau has none of these).
- Run game code with no deadline, or let it change what other game code relies on (the libraries, `solis`, another file's globals, or the globals of a function that isn't its own: there is no `getfenv` or `setfenv`). Solis's own Lua is all made before any game code runs (`Luau::new`), never later from globals game code might have reached.
- Let game code's text escape its memory limit without a cap (said lines, events, error messages, a screen's view).

## Depends on

`reflect` and glam; the Lust compiler (`lust`, without its default features, pinned to a commit) and `mlua` with Luau. For what game code reaches: `physics` (rays and 2D characters' state), `input` (actions), `tiles` (tile maps' cells), `animation` (atlases' crops), `ui` (screens' limits and views) and `area` (the built-in components, and `lust_guard`, which checks Lust before the compiler sees it).

## Status

Phase 4, M1: the description files, gathering and checking. M2: running Lust components. M3: events, and Rust components. M4: swapping new code into a running game. M5: Lua components. The runtime's parts: `runtime.rs` (the `Runtime`), `luau.rs` (the sandbox and deadlines), `lust_program.rs` (the loaded Lust), `ticking.rs` (a tick's phases and delivering events), `game.rs` (shards), `lua_components.rs`, `host.rs`, `convert.rs`. Phase 4 review: the stability fixes above, where it meets the editor (sends checked at the sender, left-out names, places of components), and speed (batched syncs, bytecode from the worker, cached Lust methods, fewer clock reads). Phase 5, M3: game code on every core (`Game`). Phase 5 review: limits on what's kept and a sticky time limit; all-or-none loads and swaps; shared component names in `Order`; the first shard on the caller's thread; a mixed hash for shards. Phase 7, S3: `solis/sound` (`playSound`, `playSoundAt`, `playSoundOn`, `stopSoundsOn`) as `Change::Sound` and `Change::StopSounds`, at most `MAX_SOUNDS` a shard a tick; nothing comes back. Phase 9, D3: `playClip` and `stopClip` (`solis/animation`, `Change::PlayClip` and `Change::StopClip`), and events the engine sends (`describe::ENGINE_EVENTS`: `AnimationCue` and `ClipFinished`, declared in the description file and brought in with `fetch`), delivered first in a tick's first round (`Game::tick_with_events`).
