# script

**Layer 1 · Engine**

Game code ([decision 0028](../../docs/decisions/0028-lust-runs-as-luau-while-editing.md)): a project's Lust, checked and turned into Lua by the Lust compiler (used as a library), and its Lua components, run together in Luau while the game plays.

## Purpose

- **The engine described to Lust** (`describe.rs`, [decision 0016](../../docs/decisions/0016-how-lust-joins-solis.md)): `NATIVES` lists every native method Solis gives game code. `descriptions` turns it into the Lust files a project gets in `assets/solis/` (`world.lst`, `entity.lst`), so they always match the engine.
- **A project's code** (`code.rs`): `gather` reads every `.lst` and `.lua` file in the assets within limits (1 MB a file, 16 MB and 10,000 files in all, hidden folders skipped). `check` runs Lust's checker from `main.lst` and gives back every mistake as a `CodeProblem` with file, line and column. `compile` also starts the code on its own (no world) to read its components' schemas into `Compiled::schemas` (and where each is written, `Compiled::places`), so the editor never runs it on the frame. The start's `send`s go nowhere, and the natives are lent while it and the starting values run. Lust itself refuses code nested more than 150 levels deep (brackets, blocks, operators in a row) and runs on a stack of its own (2.0.0-alpha.35); `compile` also runs on a thread with a 64 MB stack, for Luau compiling what Lust made. A `vec3` is a Luau vector in Luau, in Lust and Lua alike (Lust's `vectors` must say `"luau"`, checked at load). Both are meant for a worker thread.
- **Speed:** the interrupt that keeps the time limit reads the clock once in 32 interrupts; each Lust component's `update` and `handle` are looked up once when the code loads (Lust's classes don't change while it runs; Lua's can, so they're looked up each time); an event's `on_` name and its values for Lust are made once for every component it reaches; vectors handed to game code are pre-sized tables.
- **On every core** (`game.rs`, [decision 0033](../../docs/decisions/0033-game-code-sees-the-start-of-the-tick.md)): a `Game` holds one `Runtime` per shard, each with its own Luau, the same code and the entities whose ID falls to it (the ID mixed with splitmix64's finalizer, modulo the shard count: spawned IDs are all odd, so the raw ID would leave shards idle). The first shard runs on the caller's thread, working while the others do; more run on threads of their own, sent jobs over channels. Loading and swapping are all or none: a shard that fails takes every shard back (unloaded, or the last code swapped in again). `len` is counted once until components are added, removed or the code changes. During a tick each phase (the updates, then each round of events) reads a `WorldView` made at its start (places, names, the time) plus the component's own changes, and keeps what it writes (`Change::Move`, `Change::Turn`, said lines, sent events) with an `Order` (entity ID, or the event's number, then component name and sequence); the `Game` sorts them and lands them in the `GameWorld` at the phase's end. So the same game gives the same world, Console and events on 1 shard or 32. `Game` offers what `Runtime` does (`load`, `swap`, `sync_many`, `retain_only`, `retain_on` for many entities in one trip, `values`, `tick`); time limits, the tick budget and failures work per shard.
- **The sandbox** (`luau.rs`): one Luau per `Runtime`, with a 64 MB memory limit and deadlines: 100 ms per call, 250 ms for all of a tick on one shard (`TICK_LIMIT`: past it the tick is cut short and `Ticked::pause` asks the editor to pause), 1 s for all of a load's starts (`LOAD_LIMIT`; compiling isn't counted). Every place Solis touches game code's tables runs under a deadline or reads and writes raw, so no metatable can hang it. The libraries and the prelude (`component`, `vec3`, `solis`) are read-only, and the Lust and each Lua file get globals of their own that fall through to them. `LUST_NATIVES` lives in the Lust's globals; `solis` reaches the natives through a function only Solis holds.
- **Running components** (`runtime.rs`): a `Runtime` loads the Lua in that Luau, from the Luau bytecode `compile` made on the worker (`Compiled::bytecode`) when it has it, so loading on the frame skips compiling. It reads each component's fields into a `reflect` schema (starting values from a fresh component), makes and syncs running components from the area's values (`sync` sends only fields that changed, so values the game changed are kept, and does nothing at all when nothing did; `sync_many` does a batch with the natives lent once, in `syncing.rs`; `retain_on` stops one entity's components), and runs ticks: entities in ID order, components in name order. The native methods reach the game through a `Host`, lent once per tick in a `LUST_NATIVES` table that exists only while game code runs. A component that fails stops alone, and its failure points at the Lust (`Failure`). `runtime.rs` keeps the runtime itself; `host.rs` the `Host` and the natives; `convert.rs` values between `reflect` and Luau.
- **New code while running** (`Runtime::swap`): the new chunk is loaded into the same Luau and each running Lust component gets its code in place (Lust's `swap`), keeping field values by name; what changed and what started over come back as `Swapped`. If the new code's start fails, the old keeps running; if giving the running components the new code fails partway, they all start again from the area's values, with a note.
- **Events** (`events.rs`): Lust's `send` and Rust components queue an `Event`; after each tick's updates (and the moves they made) the events are delivered in rounds, in the order sent, to each component on the entity in name order; events sent in a round make the next round, cut off after `MAX_DELIVERIES` (10,000) in a tick (said once until the code changes). At most `MAX_WAITING` events wait at once, holding at most `MAX_WAITING_BYTES` of text: past that a Lua or Lust `send` fails, and `Context::send` returns false. A `send` from Lua or Rust is checked against what the Lust declares the event carries: a wrong one isn't sent, and the sender is named (Lua: an error in it; Rust: `Context::send` returns false, and the Console says why, once). Numbers in an event no Lust declares are floats. A failure handling an event is reported once per component until the code changes, and leaves it running. What game code says is cut to `MAX_SAID_BYTES` a line and `MAX_SAID_LINES` a tick.
- **Limits on what's kept** (`MAX_KEPT`, `MAX_SPAWN_BYTES`): kept changes live outside Luau's memory limit, so each shard keeps at most 200,000 changes and lines and 4 MB of spawned assembly names a phase; past them they're dropped, and the `Game` says so once (until the code changes). At most `MAX_SHARDS` (16) shards. The time limit is sticky: once a call is past its deadline every interrupt raises, so `pcall` in a loop can't hold it off.
- **Spawning** (`spawn(file, place)`, `despawn(entity)`, `frameTime()` in `solis/world.lst`; [decision 0035](../../docs/decisions/0035-game-code-spawns-into-the-area-while-playing.md)): on several cores `spawn` gives back an ID made from its place in the tick's order and the time (FNV-1a, so the same on any number of shards) and keeps `Change::Spawn`; `despawn` keeps `Change::Despawn`; the host makes them. `frameTime` reads `WorldView::frame_time`.
- **The time limits' interrupt** (`interrupt.rs`, [decision 0034](../../docs/decisions/0034-a-raw-interrupt-for-the-time-limits.md)): set on Luau directly, not through mlua (whose wrapper cost a fifth of game code's time): it finds the running clock through a thread-local that `Clock::limited` sets while a call runs (`Watching`), and raises the clock's error. The only module where Solis's own code may be `unsafe`.
- **Firing** (`fire` in `solis/world.lst`, `solis.fire` in Lua, `Host::fire` from Rust): a `Shot` the host is given; on several cores it's kept as `Change::Fire` and landed in order with the moves.
- **Left out** (`Runtime::leave_out`): Lust and Lua components the editor refused (their name is one of the engine's own, or a Rust component's) don't run; a Rust component of that name does.
- **Lua components** (`lua_components.rs`): every `.lua` file in the assets is syntax-checked on the worker (`compile`), then run in the same Luau; `component(name, fields)` makes a class (fields in order, with kinds and starting values), `solis.` reaches the natives and `solis.send` sends events, `on_Name` functions handle them, and `vec3` makes vectors that add and scale. They tick, handle events and swap like Lust's (`swap_classes`). A field can't be called `me`, `update`, `on_…` or `__…`, which would hide the entity or a method.
- **Rust components** (`rust_component.rs`): a game's `RustComponent`, made from a `RustKind` (schema and constructor), runs in the same ticks and order and sends and handles the same events through a `Context`. A panic in one (making it, updating it, giving it changes, reading its values) is caught and stops only it.

## Must never

- Crash on any code, however damaged: a panic inside the compiler is caught and reported as a mistake (fuzz-tested).
- Read files beyond its limits, or follow links to folders (they could loop).
- Let game code reach files, programs or the network (Luau has none of these).
- Run game code with no deadline, or let it change what other game code relies on (the libraries, `solis`, another file's globals).
- Let game code's text escape its memory limit without a cap (said lines, events, error messages).

## Depends on

`reflect` and glam; the Lust compiler (`lust`, without its default features, pinned to a commit) and `mlua` with Luau.
