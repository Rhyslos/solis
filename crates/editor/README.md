# editor

**Layer 2 · Editor**

The editor's interface, as decided in [decision 0004](../../docs/decisions/0004-editor-layout.md): the one-row top bar (menus, document tabs, Play and Build), the dockable panels (Viewport and Game, Area and Layers, Properties, Library and Code, Console and Problems), the controls in the viewport's corners, the icons (drawn in code, in `icons.rs`), and the theme. Interface text is Inter and monospace text JetBrains Mono (both OFL, in `assets/fonts`, licences in `licenses/fonts`).

## Purpose

Draw the editor with egui and egui_dock, keep its state between frames (the panel layout, the chosen tool, the accent colour, the camera, the console), and tell the app what to do through `WorkbenchAction`s.

**Where things are:**

- `workbench.rs`: the editor's state, and `show`, which draws a frame and returns the actions.
- `top_bar.rs`: the menus, document tabs, Play and Build.
- `panels.rs`: draws each docked panel and the bits panels share.
- `area_panel.rs`, `properties.rs`, `console.rs`: those panels' contents.
- `viewport.rs`: the viewport, its views (one, two or four, each with its own camera) and their corner controls.
- `layout.rs`: the standard layout (Reset layout), and restoring a saved one.
- `settings_window.rs`: Edit > Settings…, the editor's settings a page at a time, with a search box (decision 0061), and the project's (This project > 2D: the project's `area::pixels::PixelSettings`, saved with `WorkbenchAction::SavePixels`; decision 0062).

Tests of the whole editor (drawn with egui_kittest, without a GPU) are in `workbench_tests.rs`. `proptest-regressions/` holds the random cases the invariant tests (`invariant_tests.rs`) once failed on, which proptest runs again first; it is written by proptest, so it has no README. `src/README.md` lists every file in `src/`.

`look.rs` holds the viewport's look (standard, stylized or unlit). `document.rs` holds the open area (a `area::Area`), its component registry, the selection and the undo history; the area can only be changed through `Document::edit`. `Workbench::register_component` is the public way to add a component schema (game code in Phase 4, plugins); Properties' Add component menu lists every registered one. The Area panel draws only the rows in view. Assemblies the area uses are held as their files (`Workbench::set_assembly`); copies are expanded and collapsed with `area::assembly`, and Properties shows each copy's changes in bold with Revert and Apply. The Area panel (`area_panel.rs`) keeps its own view state (`AreaPanelState`: search, folded, hidden and locked entities), never saved and never an undo step; `menu_items.rs` holds the Edit and Entity menus' items, shared by the top bar and the Area panel. `commands_many.rs` holds Properties' commands for several entities at once and copying and pasting components. `library.rs` draws the Library and Code panels (folder tree, thumbnails or a list, search, drag and drop) and returns `LibraryRequest`s; `workbench_library.rs` turns them into actions for the app and places dropped assets where they were dropped. `picking.rs` decides what a click or a box in the viewport selects; `gizmo.rs` (adapted from Aventail) is the move, rotate and scale gizmos' maths; `transforming.rs` turns a drag into new transforms, with snapping; `screen.rs` holds the rays and projections between the screen and the world; `viewport_tools.rs` handles the mouse in the viewport (clicks, boxes, gizmo drags), draws the gizmo and the selection's outline, and holds the snapping corner; `workbench_tools.rs` is the workbench's side of it ([decision 0025](../../docs/decisions/0025-picking-and-gizmos.md)). `commands.rs` holds everything the editor does to the area (import, add, delete, duplicate, reparent keeping the world position, move here, frame, Properties and Area panel changes), each turned into edits as one undo step. `inspector.rs` draws any component's fields from its schema; `properties.rs` uses it and returns `PropertyRequest`s (and the Area panel `AreaRequest`s) that the workbench applies, so panels never change the area or the selection themselves. `area_view.rs` works out what the viewport draws from the area (models, the sun, lamps placed in the world, the environment): again only when the area, the models or what's hidden changed; the game's view each frame, its models in jobs (decision 0031). `models.rs` holds what the editor knows about imported models, by asset ID (the app holds them on the GPU), and the lights a model's file carries. `console_commands.rs` reads and runs the commands typed in the Console's command line (`console.rs` draws it, with its history and Tab), through the same editor commands as the menus, so each is an undo step. `profiler.rs` is the Profiler panel: each frame's CPU time split into game code, the world, preparing to draw, drawing and the rest of the editor (timed in `Workbench::show`, `run_game` and a timing wrapper around the renderer), with the GPU's own times and counts from `ViewportRenderer::take_report`. `problems.rs` finds the area's mistakes for the Problems panel (missing models and assemblies, unknown components, missing parents, entities inside themselves), again only when something they depend on changes. `play.rs` runs the area as a game: Play keeps a copy of the document and builds a `world::World`, Stop puts the copy back (keeping the components known now, which code changed while playing may have changed), and saving and opening wait meanwhile; `game_code.rs` puts the game's code's components in the registry (a name already taken is a problem, and that component doesn't run) and `play.rs` lands what game code spawned and despawned at the end of each tick, in order, as changes to the area that aren't undo steps (`Document::edit_by_game`, assemblies found by their file or name in the Library; decision 0035) and into the world at once; what starts and swaps spawn waits in `Playing::pending` for the next landing, and runs the code in play mode on every core (a `script::Game`, given the world through `PlayWorld`: a view at the start of each phase, its index kept while the world's `revision` doesn't change, and the phase's moves landed after): new code while playing is swapped into the running game first, and only taken in if it starts there; Save games (decision 0038): `save_game.rs` writes the running game as a save (`Save`: the area with the game's places, running components' values, input actions, projectiles, physics bytes, in checked sections) for game code's `saveGame`, through the app, and `Workbench::load_game` puts one back (from `loadGame` or Play > Load a save…): the world rebuilt and restored, game code started and given its saved values, the area shown as saved without undo steps, Stop still going back to before Play. Input (decision 0037): `play_input.rs` gives the game the mouse and keys when the Game panel is clicked while playing (the pointer held and hidden; Esc, Stop or losing focus gives them back) and feeds `input::Devices` meanwhile, with the editor's own keys off; `run_game` samples one `input::Frame` per tick for game code (`WorldView::input`), or takes it from a recording being played back, and makes game code's rebinding (on `Playing::bindings`, a copy of the project's for the play). Play > Play and record inputs keeps each tick's frame and checksums (`input::Recording`), saved on Stop through the app; Play > Replay a recording… plays one back with its seed and pauses with whether it matched, or the tick it stopped. `input_window.rs` is Edit > Input actions…: binding by pressing the key or button, saved through the app at once. A selected entity's `Collider` is outlined in the viewport as its shape (`viewport_tools::collider_lines`, `Outline::Collider`). The Console's `seed` fixes or shows the game's seed (`Workbench::fixed_seed`; otherwise each Play has a new one) and `checksum` shows the world's and game code's checksums. Physics steps once per tick after game code, and a tick of physics past `PHYSICS_LIMIT` (250 ms) pauses the game and says why. `game_panel.rs` draws the Game panel through the first camera, drawn between ticks while playing (`World::placed_between` at `World::progress`; as it is while paused); Step (`Workbench::step`) runs one tick while paused; its `GameScene` is made again only when the world's `changes` number, the models or the play state change. A move and a turn of one entity in a row land in one lookup (`PlayWorld::apply`). `camera.rs` holds the viewport camera, how it flies, and flat views (Top, Front, Right: slid and zoomed instead) ([decision 0009](../../docs/decisions/0009-fly-camera-controls.md)). The viewport turns each frame's mouse and keys into a `FlyInput`, and `Camera::fly` does the maths, so tests can fly the camera without a window.

## Must never

- Be needed by a game: games ship without the editor
- Touch the window, the GPU or files directly: the app does that, through actions and the `ViewportRenderer` it hands in
- Hard-code the program's name: it comes from `AppInfo`

## Depends on

`reflect` and `area` (the document it edits), `world` (the running game), `sound` (sound events' settings), egui, egui_dock, glam, serde and chrono. Never `render` or `asset_db`: the app connects those.

Phase 3: picking and gizmos in the viewport, the Area panel and Properties for several entities, the Library, console commands and Problems, play mode and the Game panel, several views and flat views. The panels not built yet say what arrives in which phase. Phase 7, S1: sound files in the Library (a teal stripe, their waveform, ▶ to listen) and in Properties when picked there (`sound_view.rs`: the waveform with a playhead, Play and Stop, length, channels, sample rate, format, and whether it's streamed); the app measures and plays them, and the editor asks with `WorkbenchAction::PlaySound` and `StopSound`. Phase 9, D1 (decision 0062): the 2D view (`ViewKind::TwoD`: `Camera::seen` sets its height from its whole-step zoom and puts its edges on whole screen pixels; the tile grid; `viewport_tools::pixel_corner` with the grid, Snap and Zoom; moves snapped by `transforming::snapped_in_2d`; dashed frames for 2D cameras from `AreaView::screens`), Add camera making a 2D camera there, the Game panel drawing through a 2D camera (`game_panel::pixel_camera`, `ViewportView::pixel`), and Settings > This project > 2D. Tests: `two_d_tests.rs`.
