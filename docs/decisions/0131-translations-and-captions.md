# 0131. Translations and captions: keys as the project's names, Fluent files per language, the main language as the fallback, a caption screen Solis draws

- **Status:** Accepted (builds on 0065, 0081, 0087, 0091, 0124, 0128, 0129 and 0130; the project lead asked for the recommended answer to every choice while they slept, 2026-11-18)
- **Date:** 2026-11-19

## Problem

Stage 1's milestone before the dialogue system (decisions 0122 and 0124; [report 07](../reports/after-the-rethink/07-shared-5.md), M4) is translations and subtitles: the game's text in several languages, a check for missing lines, and captions for sounds and speech. The dialogue system needs keys made once and never changed, the main language working with no translation files, the translators' spreadsheet, and a caption screen it can keep a voice line's words on for as long as the voice plays. The overnight sketch (`mock-3.png`) shows the languages with how much of each is translated, the lines side by side with a missing one marked, and the player's subtitle settings.

## Options

- **How code names a line** (guideline 3): a string key (`"shop.welcome"`, misspelt silently), or the key as one of the project's names, `Text.Shop.Welcome`, a mistake before the game runs when misspelt (recommended).
- **How the text is kept** (the research's question 3): Fluent files per language, the format translators know, with plurals and values in each language's own shape (recommended); `.po` files (the source text as the key: fragile); one data table per language (plurals and values would need Solis's own rules).
- **Reading Fluent:** the `fluent-bundle` and `fluent-syntax` libraries (Apache-2.0 or MIT; they pass `cargo deny` and bring CLDR's plural rules for every language), or Solis's own small reader with its own table of plural rules.
- **Writing systems** (question 2): Latin, Greek and Cyrillic now, Chinese, Japanese and Korean through fallback fonts, right-to-left later (recommended); all now; or Latin only.
- **Captions:** a screen each game writes, or a ready-made one Solis draws over every game screen (recommended), shown as the player's settings say.

## Decision

- **A line's key is one of the project's names.** A key is a group and a name, more parts if wanted, each a name Lust can use: `Shop.Welcome`, `Menu.Options.Volume`. Every line of the main language is an option of `state Text` in `solis/project.lst`, its parts' first letters made capitals as files' are, so `World:text(Text.Shop.Welcome)` is checked before the game runs. A key is made once and never changed: a new wording keeps its key, and renaming means a new key.
- **Each language's text is in Fluent files**, `locale/<language>/<group>.ftl` (any file in the language's folder may hold any key; a new key goes in its group's file, `shop.ftl`). Fluent's names can't hold dots, so a key's dots are dashes there: `Shop-Welcome = Welcome, { $name }!`. Plurals are the translator's, in their language's shape: `{ $count -> [one] … *[other] … }` picks English's one or other, French's (0 and 1 are one), Polish's one, few and many. Read with **`fluent-syntax`** and put together with **`fluent-bundle`** (and `unic-langid`), registered and walled in the new `translations` crate (layer 1); direction marks around values are off, since text layout doesn't lay right-to-left text out yet. Limits: 4 MB a file, 10,000 characters a line, 100,000 lines and 1,000 files a language, 256 MB in all; a file past them is left out with a note; fuzzed (`fuzz/fuzz_targets/translation_file.rs`).
- **The main language is the fallback.** `languages.lst` (`level::languages`, a Lust data file, version 1) lists the project's languages, the main one first; a project without it is written in English alone. A line missing in a language shows the main language's; a key with no line anywhere shows the key itself. So a game works with no translations at all.
- **Game code** (rule 25): `World:text(Text.Shop.Welcome)` gives a line in the player's language. A line that takes values is a method of its group's object, written by the editor into `solis/texts.lst` (rule 4): `ShopText:welcome(name, gold)`, its values in the order the main language first uses them, a value that picks a plural or goes through `NUMBER` a `float`, any other a `string`; a value left out or of the wrong kind is a mistake before the game runs. Lua: `solis.World:text("Shop.Welcome")` and `solis.ShopText:welcome("Ada", 3)` (a misspelt key stops with the nearest); Rust: `cx.host().text("Shop.Welcome")` and `text_with`. Screens call the same (`text World:text(Text.Shop.Welcome);`): Lust's `text` piece takes only text, so `text Text.Shop.Welcome` waits for Lust (asked, below). Markup (text effects) is read after translation, so a translated line carries its own.
- **Text shown is never game state.** Two players in different languages play the same game: the text isn't saved or checksummed, and the manual says game code shouldn't let a line it reads change the game.
- **Data tables' translated text columns are real.** Each cell of a column marked translated has a key, `Items.IronSword.description` (the table's, row's and column's names when it was made); a table, row or column renamed after keeps the name its keys were made from (`key = "IronSword"`), so **tables are version 2** (Breaking). A cell's main-language text is its table's; the other languages' are in `locale/<language>/items.ftl`. Game code reading `Items:row(Item.IronSword).description` gets it in the player's language; Rust's `RowRef::translated(column, texts)`. Tables' cells aren't options of `Text` (a table of 100,000 rows would make a state no one names by hand).
- **The player's language** is in the player's settings (decision 0091's file: `language nb`): their choice, else Windows' language when the project has it (`sys-locale`; the same language, `nb` for `nb-NO`), else the main one. Game code offers it with `Screens:setLanguage(Language.Nb)`, `Screens:language()` and `Screens:languageName(Language.Nb)` (`Norsk`); `state Language` lists the project's languages. A change shows from the next tick: every text, screen, table row and caption.
- **Project settings › Languages:** a row per language with its code, how much is translated (a bar and the count missing), the main one's chip and ⋯ (Make main, Show in Translations, Remove, which keeps the files); + Language with the languages Solis knows and any code typed; Open the Translations tab; **Export spreadsheet** (`translations.csv` in the project's folder: `key`, the main language and a column per language, every field quoted, quotes doubled, line breaks inside quotes) and **Import** (each language's column for each key the project has, where it differs; a table's main text stays its table's). Beside them, how game code reads the text, and the player's subtitles and captions as they're used while playing in the editor.
- **The Translations tab** (a document tab beside the level's view): every key, the main language and one other chosen at the top, missing lines marked, the search, Missing only and + Key, built on the data tables' grid (rule 21: `TableEditor` with a sheet of lines, whose keys can't be changed) with its keys. Typing in a cell writes the language's file (text that isn't Fluent is refused in plain words; empty takes the line out); undo writes it back.
- **The check** (Problems): each file's mistakes at their lines; the lines each language is missing (a count, the first few named, the list in the tab); lines of the main language nothing uses (read from the game's code and screens, `Text.Shop.Welcome`, `ShopText:welcome` and `"Shop.Welcome"`, and sound events' captions); and a translation whose values don't match the main language's.
- **Subtitles and captions.** A sound event (`.solsound`, **version 2**, Breaking) gains an optional **caption** key and **speaker** key. Solis draws a **ready-made caption screen** over every game screen (`ui::captions`): a sound heard (chosen to play, in range, on a bus game code hasn't set to 0) with a caption shows its words while the player has **captions** on; one with a speaker is a voice line, `Gardener: …`, shown while **subtitles** are on; each for as long as it plays (two to eight seconds), the newest three at once, low in the middle, on a box as dark as the player's **background** strength, as big as their **caption size**. The player's settings gain subtitles (on), captions for sounds (off), caption size (0.5 to 2) and background (0 to 1, 0.6), offered by game code (`Screens:setCaptions(true)` and the rest) and kept in their settings file. The dialogue system will show its lines through the same screen: `Workbench::show_subtitle` keeps a line up for a time or until `stop_subtitle`.
- **Writing systems:** Latin, Greek and Cyrillic, and Chinese, Japanese and Korean through fallback fonts, as text layout has them; right-to-left later.
- **Keys and mouse:** none new outside the grid, which keeps the data tables' keys.

## Consequences

- Data tables are version 2 and sound events version 2 (Breaking lines in CHANGELOG); older files read as before, with no kept keys and no caption.
- `translations` is a new crate (layer 1), with `fluent-bundle`, `fluent-syntax`, `unic-langid` and `sys-locale` registered (and `intl_pluralrules`, `intl-memoizer` and `fluent-langneg` beneath them).
- What game code can call grows (`World:text`, the `Screens` language and caption calls, `Host::text`, `texts`, `text_with`, `RowRef::translated`): `docs/game-code-interface.txt` is updated.
- Lust is unchanged. Asked of Lust, ready to send: a `text` piece taking an option of a state an engine marks as text, so a screen writes `text Text.Shop.Welcome;`.
- Not built: right-to-left text; a key picker for a sound's caption (it's typed); captions of a looping sound kept while it loops (shown as it starts); a key's rename (keys are made once); the dialogue's own lines (the next milestones).
