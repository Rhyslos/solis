# 0128. Data tables: a Lust file of typed rows, read-only while playing, read with checked names

- **Status:** Accepted (builds on 0065, 0077, 0079, 0081 and 0122)
- **Date:** 2026-11-19

## Problem

Stage 1's next milestone (decision 0122; [report 06](../reports/after-the-rethink/06-shared-4.md), M3) is data tables: any game's data (items with prices, crops with days to grow, enemies with health) as rows and typed columns in one file, edited as a table and read by game code with its spelling checked. The project lead approved a quick sketch on 2026-11-18 (`docs/design/overnight/mock-2.png`) and asked for every choice to take the recommended answer while they slept.

## Options

**The file:** a Lust data file of rows (the research's recommendation); Lust's own `cMap` written in a code file (no editor, and editing means editing code); a CSV file (loses types).

**How game code reads it:** a generated Lust file per table (rule 4) with the rows' IDs as a state and a class per row, its methods natives whose bodies Solis lends; the data written into the generated file as Lust values (big tables compiled with the game's code every time it changes, and held in every core's memory); one engine object taking a table's path and numbers (`Tables:int("items", 3, 2)`), which checks nothing.

**While playing:** tables as read-only constants (recommended, question 3); tables game code can change, which makes them game state (saved, checksummed, much bigger).

## Decision

- **A table is `<name>.table.lst`**, a Lust data file (decision 0081), version 1 (`level::table`): what each row is called (`rowName = "Item"`), its columns (a name, a kind, a translated mark, a choice's options) and its rows, one a line, each an ID and its cells written as text. Kinds: whole number, number, text, yes or no, a choice of the column's own options, one of the project's names (Sound, Clip, Picture, Prefab, Screen, Level, Tag), and colour. IDs and options are names game code can use (`IronSword`); columns are field names (`daysToGrow`), never `id`, a Lust or Lua word. **Limits:** 100,000 rows, 64 columns, 2,000,000 cells, 1,024 options, 10,000 characters a cell, refused in plain words when an edit passes them; a file past them keeps the first rows with a note. A damaged row, column or cell is left out or made empty with a note. Fuzzed (`fuzz/fuzz_targets/table_file.rs`).
- **Game code reads it through its own Lust file** (`script::table_code`): `data/items.table.lst` gives `solis/tables/data/items.lst` with `state Item = [Apple, IronSword, Potion];`, `state ItemRarity = [Common, Rare];` for each choice column, `class ItemRow` whose fields are all `lock` (read, never changed) and `object Items` with `method ItemRow row(Item which) native;` and `method ItemRow array rows() native;`. So `Items:row(Item.IronSword).price` is checked before the game runs: a misspelt row is an option `Item` lacks, a misspelt column a field `ItemRow` lacks, and `row.price = 3;` a change to a locked field. The table's name comes from its file's (`items` is `Items`); what each row is called defaults from it (`Item`; `weather` gives `WeatherRow`) and can be changed in the tab. A table whose names clash with another's or an engine object's is left out with a note.
- **Natives lent per table, rows made once:** each Luau makes, for the tables it's given, a `row` that keeps every row it has made as a Lua table and a `rows` that gives a new list of them in the table's order (`script::tables`), lent as `Items_row` and `Items_rows` with the other natives. Asking again is a lookup in a Lua table, never a trip into Rust. **Lua** reaches the same functions as `solis.Items:row("IronSword")` and `solis.Items:rows()`; a misspelt row stops with the nearest ID ("Items has no row IronSwrod: did you mean IronSword?"). **Rust** reads `cx.host().tables().get("Items")`, a row by ID and its cells by column (`whole("price")`, `number`, `text`, `yes`, `colour`), in order with `rows()`; the `Host` gains `tables()` (a deliberate change to game-code-interface.txt).
- **Read-only while playing:** tables are constants, not game state: not in the checksum, not in saves. Their contents' number (`script::Tables::hash`) goes into **save games (version 13, a `tables` section)** and **recordings (version 5, a `tables` line)**, so loading or playing one back with changed tables warns once in the Console. A table saved while the game runs reaches it at the next phase: every Luau makes its rows again from the new tables.
- **The Table tab:** a document tab beside the level's view on Home while a table is open (Library › New › **New table**, or a double-click on one; tables have their own icon and a sand colour, under the Library's Code filter). A bar of **+ Row**, **+ Column ▾** (with its kind), the search, what each row is called, the row count, **Import CSV** and **Export CSV**; the grid, its headings held at the top and only the rows in view drawn; under it, how game code reads the table with its own names. Cells by kind: text, a checkbox (a click flips it), a swatch and hex, the name's icon and name, a choice. Typing in a choice or a name lists what fits. A heading's right-click renames the column, edits a choice's options (cells follow a renamed option), marks text translated, changes what it holds (cells kept where their text fits), moves it and deletes it; a row's right-click adds a row, moves it up or down, copies, clears or deletes. Each is one undo step (`FileHistory`, rows shared so a step costs a pointer a row) and saved at once. Sorting by a heading and the search are for looking only.
- **Keys** (the common spreadsheet ones, inside the grid only, which keeps the keyboard once clicked): Enter edits, or keeps what's typed and moves down; Tab and Shift + Tab move across (keeping what's typed); the arrows move, Shift + an arrow picks a block; F2 edits; a key typed starts typing over the cell; Esc leaves the cell as it was; Delete empties the block; Ctrl + C and Ctrl + V copy and paste blocks as tab-separated text, which spreadsheets use. **Mouse:** a click picks a cell, Shift + click or a drag picks a block, a double-click types, a click on a heading sorts. No new global keys.
- **CSV:** Export writes `items.csv` beside the table (a header of `id` and the columns' names, RFC 4180 quoting); Import reads that file back, matching columns by name or heading and rows by ID, adding columns it lacks (kind guessed) and rows at the end, as one undo step.
- **Renaming a row's ID** renames the option in the table's Lust file; game code still naming the old one becomes a mistake in Problems, with Lust's line (as tags' rename, decision 0122's stage). Code isn't rewritten: a rename everywhere would edit the game's files behind its author.
- **Translated** marks a text column for the translations milestone; it changes nothing until then.

## Consequences

- Save games are version 13 and recordings version 5 (Breaking lines in CHANGELOG): older ones read as before, with no tables number, so nothing is warned of.
- A row's name cell left empty is `""` in game code, which matches no name; the tab shows it as "none".
- Screens can't read a table yet: a screen shows a component's values, so a component copies what it needs. Lists of rows in a component's fields wait for Lust's arrays in components (decision 0127).
- A table of 100,000 rows made into Lua whole (`rows()`) takes most of a core's 64 MB: the manual says to ask by ID where a game can.
