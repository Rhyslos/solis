# Phases 9 and 10 plan: First-class 2D (draft)

**Draft for the project lead.** 2D joins Solis as a first-class part of the engine ([decision 0054](../decisions/0054-first-class-2d.md)). The project lead is moving their own game to Solis: top-down, pixel art, frame-by-frame sprite-sheet animation, written in Lust. The project lead's words: "all the 2D tools need to be great", not okay, not barely working.

This plan follows "understand, then build" ([decision 0051](../decisions/0051-understand-then-build.md)). It was written from three studies:
- tile maps and level editing;
- sprites, animation, 2D rendering and 2D light;
- 2D physics, cameras and game feel.

It lists what each milestone builds, how it's measured, and the known problems of existing tools that each one must beat. The answers already given are at the top; the questions still open are at the end.

**Gate, part 1 (Phase 9):** the project lead rebuilds a real slice of their game in Lust:
- walk the farm;
- till, plant and water;
- crops grow over days;
- go to sleep;
- lamps glow at night.

It must be smooth, the pixels crisp, with no jitter.

**Gate, part 2 (Phase 10):**
- the 2D sample and the project lead's extended game slice;
- every speed budget met;
- the old tools' known problems (listed below), each a passing test.

## Answers (the project lead, 2026-10-27)

- **The approach:** 2D inside the same world, with real 2D tools on top.
- **Two parts, both finished:** part 1 is what a 2D game needs to move in, part 2 completes 2D. The order is about need, not quality: every milestone ships finished.
- **Compatibility first** (Phase 8, [decision 0053](../decisions/0053-compatibility-before-2d.md)), so the game is protected from the day it moves in.
- **After 2D:** a playtest export (Phase 11), then game UI (Phase 12), so the game gets real menus sooner.
- **2D physics:** Rapier2D.
- **Autotiling:** each tileset chooses its own kind (16-tile, 47-tile, edge sets or custom rules). There's no project-wide default.
- **Skeletal (bone) 2D animation:** after 0.1. Frames come first.
- **Pixel effects:** a pixel mode in the effects suite (Phase 15), for wind streaks, fireflies, bubbles and the like.

## The bar every milestone must pass

1. **Measured:** a speed budget with a scale case, on the reference card ([decision 0049](../decisions/0049-amd-first-when-a-choice-must-be-made.md)) and on the CI machines' software drivers for correctness.
2. **Beats the old tools' known problems:** the list under "What existing tools get wrong" is a checklist, and each item it touches becomes a test.
3. **Tough on bad input:** every file read (Aseprite files, tilesets, tile maps, levels) gets fuzz tests.
4. **Usable on day one:** a manual page written for someone new to game engines, and a working example.
5. **The project lead's round:** they use it in their game, and it isn't done until they say it feels right. What they find is fixed before the next milestone.
6. **One way to work** ([decision 0050](../decisions/0050-one-way-to-work-everywhere.md)): the shared Properties panel, preview tab and shortcut table. The keys are asked about first (CONTRIBUTING rule 17).
7. **Reviewed:** the three reviewers at the end of each part (decision 0027).

## The approach, in plain words

A 2D game in Solis is made of flat things (sprites and tile maps) placed in the same world as 3D, seen by a camera that looks straight at them with no perspective. That's why:
- **lamps, the sky and time of day, fog, bloom, colour grading, materials, effects, sound, saving and netcode** all work on 2D, with no second version to learn or maintain;
- **one lighting model** serves 2D and 3D. Engines that built a separate 2D lighting model left users struggling to mix the two.

Underneath, 2D still gets its own proper parts, not 3D parts bent into shape:
- a sprite and tile renderer;
- pixel units;
- a pixel-perfect camera that draws at the game's own resolution;
- crisp pixel filtering;
- tile maps;
- a painter;
- 2D physics.

## What existing tools get wrong (the checklist)

From forums, issue trackers and documentation, for tools the project lead and others have used:

- **Pixel art jitters or blurs.** Camera smoothing stutters. Sprites shimmer when the camera moves by less than a pixel. Text drifts against the pixel grid. Effects zoom into a corner when the picture is drawn small and scaled up. Settings for stretch, snap and filtering interact in poorly documented ways.
- **Changing one tile on a big map is slow,** in one popular engine about 4–5 ms on a 700 × 700 map, because physics, navigation and drawing for the area rebuild on each call. Autotiling while the game runs stutters, and can't move to another thread.
- **One collision body per tile:** wasteful, and characters snag on the seams between tiles. Falling through one-way platforms where two tiles meet is a long-standing bug.
- **Tile maps saved as one long encoded line,** which can't be merged in Git.
- **Per-cell data that only exists per tile type,** so a crop's growth stage has to live somewhere else.
- **Autotiling that silently picks a "nearest" tile** when the art is missing, and edges that look unpredictable.
- **Tile set editing spread across three panels.**
- **Y-sorting that works per layer,** not per cell, so players are drawn behind trees they stand in front of.
- **Moving platforms moved by setting their position,** so riders lag behind.
- **Rule-based autotiling** that's powerful but very time-consuming to set up, and the only way to autotile in some tools.
- **Aseprite importers that leave out slices and tilemaps.**
- **Automatic normal maps promised for pixel art:** a study of six methods found none gave satisfying results.

## Where things stand

- **The world, saving, undo, input, game code and determinism** don't care about 2D or 3D.
- **Transforms** hold a position, rotation and size. A 2D thing uses depth as its layer.
- **The editor has flat views and a flat camera** (Phase 3).
- **Physics is walled into the `physics` crate** (Rapier3D in its determinism mode, [decision 0036](../decisions/0036-physics-is-rapier-strict-on-every-pc.md)). Only that crate talks to the library, and `world` calls it in about 17 places.
- **The renderer always draws at the window's size,** with multisampling and HDR. A "pixel stage" (draw small, scale up crisply) is the main renderer change.
- **Projectiles** already draw 100,000 small things in one instanced draw (Phase 5): the model for sprite batching.
- **Atomic writes, recordings and checksums** exist; compatibility (Phase 8) adds upgraders and backups, which tile maps and levels join.
- **Phase 7's animation state machine** is built to drive any clip with frames, events and a length (decision 0054), so sprite animation reuses it.

## The rules this 2D keeps

- **Deterministic:**
  - tile changes, per-cell data, 2D physics, triggers and controllers are game state: saved, checksummed, the same on every PC;
  - randomness in autotiling is seeded by the cell's position, so art never reshuffles;
  - camera smoothing, shake, flashes and squash never write back into the game.
- **Meaning, not art, in files and game code.** Maps store what a cell *is*, and art is worked out from it. Game code says `setTile(map, cell, "tilled")`, never an atlas coordinate.
- **Batched changes.** A tile change marks its chunk. Art, collision and paths rebuild once per tick, together.
- **Pixels are sacred.** Nothing in a pixel-art game is drawn between pixels unless asked for: sprites, lights, particles, text drawn into the world.
- **AMD first** (decision 0049) for the renderer's sprite, tile and light passes.

## Phase 9: part 1, a 2D game can move in

### D1. The pixel-perfect view and the 2D editor
- **Drawing small, scaled up crisply:**
  - each 2D project has a **base resolution** (say 480 × 270) and pixels per unit;
  - the world is drawn at the base resolution plus a one-pixel margin, then scaled up to the screen in whole steps, letterboxed;
  - or **"nearest whole step, then sharp"**, for screens whose size doesn't divide evenly.
- **Smooth scrolling without shimmer:** the camera stays on whole pixels, and the finished picture slides by the camera's fraction of a pixel as it's scaled up.
- **Sharp text and menus:** drawn at full screen resolution, in their own pass.
- **Movement smoothed between ticks** (the game's fixed tick, Phase 6), the camera updated after it, and snapping to pixels only at the very end. This removes the commonest cause of jitter.
- **A warning** in Problems when a sprite rests between pixels by accident.
- **The 2D view mode** in the editor: pan and zoom, flat move handles, snapping to pixels and to the tile grid.
- **Budget:** the pixel stage under 0.2 ms at 4K.
- **Tests:** every common screen size and scale, checked pixel by pixel; a camera moving a fraction of a pixel per frame moves the picture smoothly and never blurs.

### D2. Sprites from Aseprite
- **An `.aseprite` file is an asset.** Saving it in Aseprite reloads it in Solis at once.
  - **Tags** become clips, with their direction (forward, reverse, ping-pong) and repeats.
  - **Slices** become pivots, 9-slices, hitboxes and attach points (where a held tool goes).
  - **User data** on frames becomes events (a footstep, a swing that lands).
  - **Layers** can stay separate, to swap clothing and tools, or carry normal and glow maps (part 2).
  - **The palette** becomes a palette asset.
- **Atlases packed automatically,** with padding and extruded edges so nothing bleeds.
- **The batcher:**
  - every sprite's place, frame, flip, tint, palette row and flash are kept per copy in one buffer;
  - sprites are drawn in a handful of draws;
  - cut-out transparency, so pixel art writes depth.
- **Front and behind for free:** depth is worked out from a sprite's foot position, so things lower on screen are drawn in front with no sorting. Only truly see-through sprites (glass, smoke) are sorted.
- **Built in:** flip, tint, hit-flash and outline.
- **Budget:** 100,000 sprites at 60 fps on the reference card.
- **Fuzz tests** for the Aseprite reader.

### D3. Frame animation
- **Clips:** per-frame timing from Aseprite, loop, ping-pong and play-once, and events.
- **Driven by Phase 7's state machine**, the same one 3D uses: idle, walk, use tool, in four or eight directions.
- **Previews:** the Library and Properties preview clips with a play button.
- **Game code:** `playClip(entity, name)` and the state machine's parameters.

### D4. Tile maps that change as you play
- **Layers of meaning:** ground, decoration, and things drawn above the player. Each cell holds a terrain name from the project's list ("grass", "tilled", "water", "fence").
- **Per-cell data:** a small table per chunk of named values per cell (crop, growth, watered), saved and checksummed. Readable and writable from Lust, Rust and Lua:
  - `tileAt`, `setTile`;
  - `cellValue`, `setCellValue`;
  - `cellsWhere`, for "every watered crop".

  Crops don't need an entity each, though a plant that needs animation or behaviour can still be one, tied to its cell.
- **Batched changes:** a change marks its chunk (32 × 32). Art, merged collision and later paths rebuild once per tick, off the main thread where possible.
- **Saved as readable text in chunks:** rows of short codes defined by the tileset (`.` grass, `t` tilled, `~` water), one file per map. A Git diff shows exactly the changed cells, and the art isn't stored, since it's worked out on load.
- **Budgets:**
  - 10,000 cell changes in under 1 ms;
  - a 1,000 × 1,000 map that loads in under a second and draws at full speed.
- **Fuzz tests** for the map reader. The format joins the upgrade path from Phase 8.

### D5. Autotiling and tilesets
- **Each tileset chooses its kind:**
  - **16-tile (dual grid):** art on a grid offset by half a tile, each piece picked by the four cells at its corners; the least art for smooth edges;
  - **47-tile ("blob"):** the most polished corners;
  - **edge sets:** for fences, walls and roads;
  - **custom rules:** patterns from 1 × 1 to 9 × 9, for any layout.
- **The tileset wizard:** drop in a PNG, the grid is detected, you say what kind it is (it guesses from the layout and you confirm), and it's marked up against a template. Template images to draw over come with Solis.
- **No silent guessing:** a **missing tiles** view shows what art the set still needs, and when a tile is missing the map says so instead of quietly picking another.
- **Randomness:** variations and weights, seeded by cell position.
- **Animated tiles** (water, flowers): frames with a speed, using D3's clips.
- **Changing a tileset's kind or art** redraws every map, because maps store meaning.

### D6. The tile painter
- **Tools:**
  - brush, rectangle, line and fill, each terrain-aware;
  - an eyedropper that copies an area;
  - flip and rotate;
  - a modifier to place one exact tile without autotiling;
  - a switch between the art and the meaning underneath.
- **Each stroke is one undo step.**
- **Painting stays smooth on large maps:** art redraws a moment behind the brush.
- **One panel:** tileset, tools and layers in one place, using the shared Properties panel and shortcut table. The keys are asked about first.
- **Budget:** painting on a 1,000 × 1,000 map at the editor's frame target.

### D7. 2D physics and top-down movement
- **The 2D world:** Rapier2D in its determinism mode, walled into `physics` beside the 3D world.
- **Tile collision merged into shapes:** greedy rectangles for top-down maps, one-sided edge chains for side views.
  - Never one body per tile.
  - A test slides a box across 1,000 tile seams with no bump.
- **Triggers** with enter and exit events in a fixed order: doors, crops within reach, shop counters.
- **Movers:**
  - a shape cast with a small skin;
  - sliding along walls;
  - a moving-platform carrier that uses the platform's velocity, never a teleport.
- **The top-down controller,** a ready-made Lust component:
  - 8-way, with acceleration and deceleration;
  - diagonals at the same speed as straight lines;
  - corner sliding around tile edges;
  - every value tunable;
  - open code to read and change.

### D8. The 2D camera and feel tools
- **The follow camera:**
  - a dead zone and smoothing (smooth damping, not plain blending);
  - map bounds;
  - room transitions (snap or pan);
  - a "farm" preset (centred, held inside the map).
- **Screen shake** from a "trauma" value (shake grows with the square of it, and decays), on the drawn picture only.
- **Feel tools for game code:**
  - tweens with easing curves;
  - timers;
  - flash and tint;
  - slow-motion per entity.

### D9. Lamps and day and night on sprites
- **Sprites and tiles are lit by lamps,** with each sprite given a height so ordinary lamps light it.
- **Light worked out at the game's resolution,** so it falls on the pixel grid and stays crisp. A **light steps** setting gives a banded look.
- **Day and night tint follow the time of day,** which is game state, so a game's clock and sleeping work.
- **Budget:** 256 lamps on a full-screen 2D scene within 1 ms.

## Phase 10: part 2, 2D complete

### D10. Levels, entities and the world
- **Entities placed in levels:** typed fields, links to other entities, lists from the project's own choices (enums), resizing with limits, and counts per level.
- **Rooms on a world map,** dragged into place, with neighbours shown while painting.
- **Sort points** for tall things (trees, houses, fences), so the player walks behind and in front of them correctly, previewed in the editor.

### D11. Advanced tiling
- **Rules for decoration and variety:**
  - chance;
  - patches by noise;
  - flips;
  - spacing;
  - offsets;
  - multi-tile stamps;
  - rule groups switched on by area.
- **Scatter brushes** with weights, **reusable patterns** and **stamps.**
- **The 47-tile template.**

### D12. Pathfinding
- **A\*** over the tile map for single characters.
- **Flow fields** for many characters heading to one place.
- **A cost per cell,** so paths can be slow through mud, avoid crops, or prefer paths.
- **Only changed chunks rebuild** when something is built or dug.
- **Budget:** 500 characters re-pathing in one tick within 1 ms.

NPC schedules are the game's own code, built from these and the time of day.

### D13. Soft shadows and richer 2D light
- **A distance field** (how far each pixel is from a wall) built from the merged tile collision and marked objects, giving soft shadows from lamps.
- **Optional normal and glow layers** painted in Aseprite, or a simple automatic bevel. Flat lighting stays the default; automatic normal maps aren't promised.
- **Long shadows** from the sun's direction for top-down scenes, by stretching sprites' outlines.
- **The same distance field** later serves 2D bounced light (Phase 13) and particle collisions (Phase 15).

### D14. More movement
- **A grid-step controller:** one tile at a time, with buffered turns and turning on the spot.
- **A platformer controller,** with jumps set by height and time to the top:
  - falling faster after the top;
  - lighter gravity at the top while the button is held;
  - coyote time and jump buffering;
  - corner correction;
  - wall-jump grace.
- **One-way platforms** decided per edge, so they never fail where two tiles meet. **Slopes**, and **moving platforms** that carry riders properly.

### D15. Polish, the sample and the manual
- **Parallax backgrounds,** each layer with its own scroll speed and its own sub-pixel slide.
- **Palette tools:**
  - swaps (a palette row per copy);
  - palette cycling for water and fire;
  - limiting a scene to a palette.
- **Clean pixel-art rotation** (an edge-preserving method), for when sprites must turn.
- **Hit-stop and squash and stretch,** as feel tools.
- **Help > Make the 2D sample:** a small farm (till, plant, water, grow over days, sleep, lamps at night), in Lust, as a starting point.
- **The manual's full 2D section,** for someone new to game engines.

## What later phases add to 2D

- **Phase 11, the playtest export:** 2D games can be sent to playtesters.
- **Phase 12, game UI:** inventories, shops and dialogue, drawn crisply at screen resolution over the pixel world.
- **Phase 13, light:**
  - **2D bounced light** by radiance cascades: light glowing around corners and off coloured walls, and lanterns lighting a room. Its cost depends on screen size, not on the number of lights; a published version runs a 512 × 512 scene in under 2 ms on a laptop card;
  - the real sky and time of day over 2D worlds;
  - bloom and grading.
- **Phase 14, materials:** sprite materials in the graph (shimmering water, swaying grass, glowing crystals).
- **Phase 15, effects:** the pixel mode (wind streaks, fireflies that light the field, bubbles, rain, snow, dust, leaves, sparkles), particles colliding with the 2D distance field.
