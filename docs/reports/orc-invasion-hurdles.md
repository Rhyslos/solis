# Hurdles from making Orc Invasion

A report by a session that made **Orc Invasion**, a small top-down action RPG, in Solis and Lust, written 2026-11-19 and checked against `main` at 621514d. The project lead asked for every hurdle to be fixed in the plan (2026-11-20): what goes where is in [the game stages](../plans/game-stages.md#fixes-from-making-orc-invasion) and [decision 0133](../decisions/0133-fixes-from-making-orc-invasion.md). The report is kept as written.

## About this list

These are the 27 hurdles I hit making Orc Invasion, a small top-down action RPG in Solis and Lust. Each one comes with what happened, how I got around it, and what would fix it. I checked them against Solis main as of today (commit 621514d): none has been fixed since.

**Ratings**

- **High:** a game that checks out can still break when played, or the workaround cost hours.

- **Medium:** there's a workaround, but it makes game code longer or harder to read.

- **Low:** a paper cut.

**The five I'd fix first**

1. Screens can fail to start because of a Lua limit (B1). The project check passes, but the screens fail as soon as play starts.

2. No way to choose an animation from an action plus a direction (M1). The knight needed 300 lines of lookup tables.

3. Game code can't read another entity's component, or reach a one-off entity without a string (M5, M6). Every small question became an event, and World:find("Game") breaks the "no string names" rule.

4. The 2D file formats are only documented in the Rust source (D1). Writing a level or a sprite sheet by hand meant reading aseprite.rs, sidecar.rs, hash.rs and text.rs.

5. Playing a game headless is only possible inside Solis's own Rust tests (T1). A command for it would let anyone test their game.

## Bugs

### B1. Screens fail to start: "Out of local registers" (High)

- **What happened:** the game's code checked out, but on Play every screen failed with Out of local registers when trying to allocate manaJump: exceeded limit 200. The screens' Lua puts every top-level method of every file a screen fetches into one function, and Lua allows 200 locals per function. My knight clip lookup had 21 methods, and the HUD fetches the knight's file, which pulled them in.

- **Workaround:** I folded the 21 methods into 2, each a big nested check.

- **Suggestion:** generate methods as fields of a module table, or one function per file, so the count can't overflow. Until then, --check-project should build the screens' program too (see T2), so this shows up as a Problem, not at play time.

### B2. A colour with transparency is silently not drawn on a screen (Medium)

- **What happened:** background "#1a1c2ccc" drew nothing, so the dialogue text sat straight on the grass. LUST.md says "#2f9e4480" is allowed. Workaround: solid colours only. Suggestion: draw the alpha. If that's not supported yet, report it in Problems instead of dropping the background silently.

### B3. Spawned copies are named after the prefab's file, not its root's name (Low)

- **What happened:** the raider prefab's root is named "Orc Warrior", but every orc spawned from Prefab.Characters.Orcs.Warrior is called "warrior" in the Level panel and in saves. Suggestion: use the root part's name, as placing the prefab in the editor does.

### B4. Opening a project starts on an empty "Untitled level" (Low)

- **What happened:** with a fresh settings folder, opening Orc Invasion showed an untitled level, though the project has one level ( Level/main). A newcomer presses Play and sees nothing. Suggestion: open the last level used, or the project's only level, or the one named in project settings.

### B5. Eleven warnings on every first open (Low)

- **What happened:** the Console showed 11 warnings that all said the code had mistakes while the project's names were still loading. Then: "The game's code has no mistakes now." It reads as broken. Suggestion: don't check game code until the names have been read once, or fold these into one "still loading" line.

## Missing game-code calls

### M1. No way to choose a clip from an action plus a direction (High)

- **What happened:** the knight has 10 actions × 8 directions × 2 looks = 160 clips. Lust can't build Clip.Sprites.Knight.WalkNE from "Walk" and a facing, and there's no call to ask for "the Walk clip, facing north-east". Workaround: game/knightClips.lst and game/creatureClips.lst: about 300 lines of nested check s, generated by a script to avoid typos. Suggestion: read an Aseprite tag naming rule such as walk/NE as one clip with directions, and add animate(Clip.Sprites.Knight.Walk, facing) with a direction state from solis/entity. Animators already know directions, so the same idea could reach plain sprites.

### M2. No way to switch a character to another look (Medium)

- **What happened:** the mana-charged knight is a full second set of animations. There's no call to change a sprite's sheet while playing, and an animator plays one sheet, so a second animator file can't be switched to either. Workaround: both looks share one Aseprite file, with the mana tags prefixed mana. That doubled the lookup in M1. Suggestion: setSheet(Sheet.Sprites.KnightMana), or animator variants (a switch parameter that picks among clip sets).

### M3. A dead body keeps its collider (Medium)

- **What happened:** fallen orcs, the wizard and the captain still block movement. A key dropped where the captain fell sat inside his collider, and the knight couldn't get close enough to pick it up. Workaround: keys drop 0.7 m in front of the body, and the pickup reach went from 0.8 to 1.0 m. Suggestion: setSolid(false), or a Collider2D.enabled field game code can turn off.

### M4. No way to hide or show a sprite (Low)

- **What happened:** I wanted the mana glow as a second sprite to switch on and off. There's no visibility call, and moving an entity away fights with its parent. Suggestion: setVisible(bool) on an entity.

### M5. Game code can't read another entity's component (High)

- **What happened:** an orc can't ask whether the knight is blocking, and a gate can't ask whether the knight carries its key. Screens can read components ( Ui:entity():knight()), but game code can't. Workaround: everything became events. A gate sends WantsOpen to the Quest, which answers Unlocked. The knight's block and parry logic runs on the knight's side when Hit arrives. It works, but it's about twice the code for simple questions. Suggestion: a read-only snapshot like screens get, as last tick left it: entity:knight(). This keeps each core's copy safe, as screens already show.

### M6. A one-off entity can only be found by a string (Medium)

- **What happened:** the story lives on the entity called "Game", and orcs, villagers and gates send to World:find("Game"), also used for the spawn markers and "Menus". This breaks the game-API guideline "never a string name": renaming the entity breaks the game silently. Suggestion: a checked name, such as an Entity state Solis writes for named entities in the level, or a way to reach a level's single component of a kind: World:the(Quest).

### M7. A spawned entity can't be given values (Medium)

- **What happened:** the wizard's fireball needs a direction, and a dropped pickup needs to know which item it is. World:spawn takes only a prefab and a place. Workaround: the fireball aims at the knight itself on its first tick, and each item got its own prefab (8 pickup prefabs instead of 1). Suggestion: World:spawn(Prefab.Pickups.Item, place, [Pickup.item = Item.KeyRed]), or a guarantee that an event sent to a just-spawned entity reaches it on its first tick.

### M8. No way to tell whether an entity still exists (Medium)

- **What happened:** a fireball sends Hit to the knight and despawns, but the knight's on Hit asks by:position(). I couldn't find out what that does for an entity that's gone, or when a despawn takes effect relative to events. Workaround: a fireball now lingers 0.2 s after hitting. Suggestion: entity:exists(), and a sentence in the manual on the order of updates, events and despawns within a tick.

## Lust language rough edges

### L1. No arrays in components (Medium)

- **What happened:** conversations are lists of lines, but a component can't keep a list, and objects can't be changed by components. So the Quest's conversations are a check on the conversation with an is i == 0? per line. Workaround: nextLine() in game/quest.lst. It's readable, but adding a line in the middle means renumbering. Suggestion: arrays of basic kinds in components (already planned, per the field-hints decision). Until then, a lock string array in a file a component can read would cover fixed lists like dialogue.

### L2. Common parameter names are reserved words (Low)

- **What happened:** event WantsOpen(entity lock, Item key) and a variable called has were refused: lock and has are Lust words. The error message is good, but these are natural names in games (a door's lock, has a key). Suggestion: allow them where a keyword can't appear (parameter and variable names), or list Lust's own words in one place in LUST.md.

### L3. Short capital names are refused (Medium)

- **What happened:** state Facing8 = [S, SE, E, NE, N, NW, W, SW]; was refused: "names can't be in capitals". Compass points are the most common direction names in games, and Solis itself turned the Aseprite tag walkSE into the clip WalkSE, so capitals are fine there. Workaround: South, SouthEast and so on, which made the clip tables longer. Suggestion: allow names of one or two capital letters, or allow them as state options.

### L4. A result that isn't used is an error (Low)

- **What happened:** World:spawn(Prefab.Effects.Fireball, place); fails with "spawn(…) gives back an entity, but nothing uses it". Spawning and forgetting is common (fireballs, drops, effects). Workaround: entity ball = World:spawn(...) with an unused variable (four times in the game). Suggestion: a warning, not a failure, or a way to say "I don't need it", such as _ = World:spawn(...).

## Documentation gaps

### D1. The 2D file formats are only in the Rust source (High)

- **What happened:** to make the game by script I had to read Solis's code for: which Aseprite features are read: cel kinds, tag repeats becoming Plays, and the feet slice as the pivot ( crates/assets/src/aseprite.rs) sidecars and their content hash ( crates/asset_db/src/sidecar.rs, hash.rs) how a level writes a placed prefab copy and its changes ( crates/level/src/text.rs) the prefab, tileset and tile map data files and their versions (the test fixtures) how a state field is stored in a level (the option's name as text) the 2D component fields ( crates/level/src/builtin/) Workaround: the fixtures in tests/fixtures/ and the two-PCs test game were the best reference. Suggestion: a manual page, "Solis's files", with one short annotated example of each. It's also what a game's own tools (level generators, exporters) need.

### D2. How an Aseprite tag becomes a clip name isn't written down (Low)

- **What happened:** I guessed that the tag walkSE would be Clip.Sprites.Knight.WalkSE and checked it in project_names.rs. The rule matters because game code names clips. Suggestion: a line in the sprite animation page: the first letter is made a capital, all- capital names are lowered, and other characters are dropped.

### D3. Writing files by hand needs IDs, and there's no way to make one (Medium)

- **What happened:** a tile map points at its tileset, a level at its sheets and prefabs, all by ID. To write them by script I made IDs myself in the right form (13 letters, the first at most F) and wrote the sidecars, with their content hashes, myself. Suggestion: solis --new-id, or let a file point at another by path ( "tiles/world.tileset.lst") and turn the path into the ID the first time Solis reads it.

### D4. Where the input key names are listed (Low)

- **What happened:** input.solinput takes names such as "Mouse Left", "Pad RT", "Shift" and "Escape". I found them by reading the standard actions in crates/input.

- **Suggestion:** a table of every key and button name in the input page.

### D5. A screen's column marked right stretches across the screen (Low)

- **What happened:** I marked the goal panel's column right to put it in the top right corner. It stretched across the whole top and covered the HUD. The rule is in LUST.md ("a row or column told center, right or spread stretches"), but it's the opposite of what the word suggests. Suggestion: a picture of this in the screens page, or a separate word for "push me to the right" (such as alignSelf right).

## Tools and testing

### T1. Headless play only exists inside Solis's Rust tests (High)

- **What happened:** the best tool for testing the game was the workbench the two-PCs test uses: open a level without a window, play it tick by tick with a gamepad set from code, and read every component's values. To use it I wrote a test file inside my copy of Solis ( crates/app/src/orc_play_tests.rs) and built the whole engine. With it I played every chapter of the game, and it found the screens bug (B1) and two gameplay bugs. Suggestion: a command for game makers, such as solis --play project Level/main --ticks 600 --inputs script.txt --print Quest,Knight. It would print the Console and the chosen components. It's also what a game's CI needs.

### T2. --check-project doesn't start the game (High)

- **What happened:** the check said "The project checks out" while every screen would fail on Play (B1). It compiles the game's code, but not the screens' program, and runs no ticks. Suggestion: build the screens' program as part of the check, and optionally ( --smoke 60) play the first level for a second and report any error in the Console.

### T3. Recordings can't be written by hand (Low)

- **What happened:** the check plays recordings in recordings/checks/, which would have been a good place for my scripted play-throughs. But they're made by recording in the editor, and their format holds expected states, so I couldn't write one. Suggestion: a plain-text input script a recording can be made from, and a way to record a check from the command line by playing a script.

### T4. The new-project template puts every PNG in Git LFS (Medium)

- **What happened:** the project's.gitattributes sends *.png, *.wav and *.ogg to LFS. Orc Invasion's 25 pictures are about 50 KB in total. LFS adds a setup step for newcomers, costs storage quota, and in my environment the upload was refused, so the push failed. Workaround: a few lines in.gitattributes keep the game's folders out of LFS. Suggestion: leave pixel art and short sounds in Git by default, or explain the choice in the new-project page, with how to turn it off.

### T5. Building on Linux needs packages nobody mentions (Low)

- **What happened:** cargo build -p app failed on a clean Ubuntu without libasound2-dev and libudev-dev. Solis is made for Windows, but CLAUDE.md asks for the checks to be run locally on Linux. Suggestion: one line in ARCHITECTURE.md or CONTRIBUTING.md: the Linux packages the build needs.
